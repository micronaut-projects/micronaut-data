An explicit ann:data.annotation.Query[] method can declare a api:data.model.Pageable[] or a api:data.model.Sort[] parameter just like a query method. Micronaut Data does not parse the SQL you write: at execution time it appends the pagination to the end of the query:

* an `ORDER BY` clause, if the `Pageable` (or `Sort`) is sorted
* the dialect specific limit and offset clause (for example `LIMIT 2 OFFSET 2` for H2, MySQL or PostgreSQL, `OFFSET 2 ROWS FETCH NEXT 2 ROWS ONLY` for Oracle or SQL Server), if the `Pageable` is paged

A `FOR UPDATE` clause at the end of the query is kept last. An unpaged and unsorted `Pageable` (`Pageable.UNPAGED`) leaves the query unchanged.

<2> A method returning a api:data.model.Page[] must define the `countQuery` member, the query that computes the total number of results. It is required at compilation time: without it the compilation fails with `Query returns a Page and does not specify a 'countQuery' member.`
<3> Methods returning a api:data.model.Slice[] or a `List` don't execute a count query and therefore don't need `countQuery`

For the `Page` method the executed queries are:

[source,sql]
----
SELECT book_.* FROM book book_ WHERE book_.pages > ? ORDER BY book_.`pages` DESC LIMIT 2 OFFSET 2
SELECT COUNT(*) FROM book book_ WHERE book_.pages > ?
----

The `countQuery` receives the same method parameters as the query (it can use any of them) and it is executed as written: the `ORDER BY` and limit clauses are never appended to it. Micronaut Data executes the count query only when the method returns a `Page` (or a api:data.model.CursoredPage[]).

WARNING: Since the clauses are appended to the query, a query that already ends with an `ORDER BY` clause can't be combined with a sorted `Pageable` or a `Sort`, it would produce an invalid query with two `ORDER BY` clauses. A query with its own `ORDER BY` clause works with an unsorted `Pageable`, for example `Pageable.from(1, 10)`, in which case only the limit clause is appended. Don't write a `LIMIT` clause in a query that receives a paged `Pageable`.

[[sortingExplicitQueries]]
== Sorting

How the sort properties of the `Pageable` or `Sort` are translated to the `ORDER BY` clause depends on the `nativeQuery` member of ann:data.annotation.Query[]:

* By default (`nativeQuery = false`) the sort properties are *entity property names*. They are validated and translated to the column names, prefixed with the entity alias Micronaut Data uses in the queries it generates. The alias is the entity name in snake case followed by an underscore (`book_` for `Book`, `book_author_` for `BookAuthor`), or the value of `@MappedEntity(alias = "...")`. The query must use that alias for the root table, otherwise it fails with an error like `Column "BOOK_.TITLE" not found`. Sorting by a property that doesn't exist fails with `Cannot sort on non-existent property path`.
* With `nativeQuery = true` the sort properties are used *as they are* as SQL identifiers: a column name, or a column name qualified with a table alias of the query. They are not mapped to columns, so use the column name (`total_pages`) and not the property name (`totalPages`). To prevent SQL injection a native sort property must consist of letters, digits and underscores, optionally separated by dots, otherwise the query fails with `Invalid native query sort property`.

NOTE: With SQL Server, if the query has no `ORDER BY` clause and the `Pageable` is not sorted, Micronaut Data orders the results by the identity of the entity because SQL Server requires an `ORDER BY` clause for the `OFFSET ... FETCH` clause.

== Cursored Pagination

A method with an explicit query can also return a api:data.model.CursoredPage[] (see <<cursored-pagination, Cursored Pagination>>). Like for `Page`, the `countQuery` member is required. For a cursored query Micronaut Data has to modify the query itself, not only append clauses:

* the identity is added to the sorting, to make it unique
* the condition on the cursor values is inserted after the first `WHERE` keyword of the query (the existing condition is wrapped in parentheses and the cursor condition is added with `AND`), or a `WHERE` clause is appended if the query doesn't contain `WHERE`

Therefore, use cursored pagination only with simple `SELECT ... FROM ... WHERE ...` queries: the `WHERE` keyword must be written in upper case, the first `WHERE` of the query must be the one of the main query (not of a subquery), and the query must not end with `GROUP BY`, `HAVING`, `ORDER BY` or `LIMIT` clauses. The sort properties follow the same rules as described above.
