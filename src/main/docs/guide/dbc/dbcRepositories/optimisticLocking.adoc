Optimistic locking is a strategy where you note the actual record state's version and modify the record only when the version is the same.

To enable optimistic locking for your entity add ann:data.annotation.Version[] annotated field with one of the types:

- `java.lang.Integer`
- `java.lang.Long`
- `java.lang.Short`
- Date-time type extending `java.time.Temporal`

The field is going to be incremented (for number types) or replaced (for date types) on an update operation.

Micronaut Data will generate `UPDATE`/`DELETE` SQL queries with a version match: `... WHERE rec.version = :currentVersion ...` and if the update/delete doesn't produce any result api:data.exceptions.OptimisticLockException[] will be thrown.

It's possible to use ann:data.annotation.Version[] in a partial update or a delete method, in this case the version needs to match the version of the stored record.

You can control conflict handling per repository method with ann:data.annotation.OptimisticLockConflict[].
The default policy is `FAIL_FAST`, which preserves the existing behavior and rethrows api:data.exceptions.OptimisticLockException[].

If you set `DELEGATE`, Micronaut Data calls a bean of type api:data.exceptions.OptimisticLockExceptionHandler[]:

[source,java]
----
@Repository
interface StudentRepository extends CrudRepository<Student, Long> {

    @OptimisticLockConflict(OptimisticLockConflict.Policy.DELEGATE)
    void update(@Id Long id, @Version Long version, String name);
}

@Singleton
class MyOptimisticLockHandler implements OptimisticLockExceptionHandler {
    @Override
    public Object handle(OptimisticLockException exception, MethodInvocationContext<?, ?> context) {
        // custom merge / retry / fallback behavior
        return null;
    }
}
----

For built-in reload+merge retry, use `RELOAD_AND_RETRY` with `maxRetries`:

[source,java]
----
@Repository
interface StudentRepository extends CrudRepository<Student, Long> {

    @OptimisticLockConflict(value = OptimisticLockConflict.Policy.RELOAD_AND_RETRY, maxRetries = 2)
    void update(@Id Long id, @Version Long version, String name);
}
----

`RELOAD_AND_RETRY` reloads the latest entity by `findById(id)`, updates the method `@Version` argument to the current value, and retries the update.
This is useful for partial updates (`id + version + changed fields`) where the method arguments already represent the desired merged state.
It also works for entity updates (for example `update(entity)`): Micronaut Data refreshes the entity argument's `@Version` before retrying.

Constraints and guidance for `RELOAD_AND_RETRY`:

* Use it for update methods that either take an entity argument or include both `@Id` and `@Version` parameters.
* The repository must support loading the latest entity state via `findById(id)`.
* This is a retry of the same requested change with a refreshed version, not a deep domain conflict merge.
* For delete methods, prefer `FAIL_FAST` or `DELEGATE` unless retry semantics are explicitly desired.

NOTE: `@OptimisticLockConflict` is only valid on optimistic-locking methods (for example, methods that include ann:data.annotation.Version[] in the update/delete signature).
