=== JDBC driver

Micronaut Data JDBC requires that an appropriate `java.sql.DataSource` bean is configured.

You can either do this manually or use the https://micronaut-projects.github.io/micronaut-sql/latest/guide/#jdbc[Micronaut JDBC] module which provides out-of-the-box support for configuring connection pooling with either Tomcat JDBC, Hikari, Commons DBCP or Oracle UCP.

=== SQL Logging

You can enable SQL logging by enabling trace logging for the `io.micronaut.data.query` logger. For example in `logback.xml`:

.Enabling SQL Query Logging
[source,xml]
----
<logger name="io.micronaut.data.query" level="trace" />
----

==== Unique Constraints

By default, JPA unique constraints are not generated. Set `schema-generate-unique-constraints=true` to create a unique index for every column annotated with `@Column(unique = true)`, for every to-one association join column annotated with `@JoinColumn(unique = true)` (also a single join column of a composite `@JoinColumns`), and for the columns of `@Table(uniqueConstraints = @UniqueConstraint(...))`, which can be any table column, including embedded and association columns (the combined columns of a composite join are made unique this way). The constraint column names are the table column names, a property name (like `firstName` for the column `first_name`) is accepted too. An unnamed constraint gets a generated name that fits the identifier length limit of all the supported databases. The unique indexes of a table are created after the table, and with the option enabled the schema validation reports missing unique constraints.

.Generating unique constraints
[source,yaml]
----
datasources:
  default:
    schema-generate: create-drop
    schema-generate-unique-constraints: true
----

NOTE: Unique indexes declared with `@Index(unique = true)` are always generated.

==== Schema Validation

In order to validate mapped entities against current schema state set `schema-generate=validate` in the configuration.
All the problems found are reported together. The following differences are errors, and the application will report them and stop:

* A mapped entity or join table does not have a corresponding table in the schema
* A mapped property does not have a column in the table
* The column type is not compatible with the mapped type. Compatible types are accepted, for example a wider integral type, `TEXT` or `CLOB` for strings, or any type name synonym (`int4` for `INTEGER`). Columns with an explicit definition (`@MappedProperty(definition = "...")`) are compared by the type name of the definition. Vector and spatial types are always verified, including the vector dimension (Oracle, PostgreSQL and MySQL) and the Oracle vector storage (dense or sparse).
* A `UUID` stored as a string in a column shorter than 36 characters
* A sequence used to generate the identity values does not exist
* An Oracle JSON relational duality view (`@JsonView`) does not exist, is not valid, has a different root table, a sub view (`@JsonSubView`) is missing under its JSON key or is an object instead of an array (or the opposite), or a JSON field of the view entity is missing or stored in a different column

The following differences are only logged as warnings, since they only fail for some values or don't affect the mapping:

* A column is shorter or has smaller precision than the mapped type
* A column nullability is different from the mapped property nullability
* The table primary key is different from the mapped identity
* A declared index (`@Index`, `@VectorIndex`) does not exist. Spatial and vector indexes are matched by their name, the declared or the generated one, since the index method is not reported by the database metadata
* A unique constraint does not exist, validated only when `schema-generate-unique-constraints` is enabled
* A vector column has a different element format (for example `FLOAT64` instead of `FLOAT32`)
* A JSON view or one of its sub views allows different operations than declared, or the view has fields or sub views not mapped by the view entity

The schema, table, column and sequence names are matched the same way as the generated SQL refers to them: an escaped name (`@MappedEntity(escape = true)`, the default) must match exactly on the databases with case-sensitive quoted names (PostgreSQL), while the unescaped names, and all the names on Oracle and H2, are matched in the database identifier case. The MySQL table names are case-sensitive when the database is (`lower_case_table_names=0`).

The schema metadata is read in bulk and validated in memory: a single call per schema reads the tables and columns, and a single catalog query per schema reads the primary keys, and another one the indexes, only when some are validated (H2, PostgreSQL, MySQL, MariaDB, SQL Server and Oracle). For the other databases they are read with a call per table, since the JDBC drivers require the table name.

Please note this option is currently regarded as experimental.

=== Setting the Dialect

As seen in the configuration above you should also configure the dialect. Although queries are precomputed in the repository some cases (like pagination) still require the dialect to specify. The following table summarizes the supported dialects:

.Supported JDBC / R2DBC Dialects
[cols=2*]
|===
|*Dialect*
|*Description*

|api:data.model.query.builder.sql.Dialect#H2[]
|The H2 database (typically used for in-memory testing)

|api:data.model.query.builder.sql.Dialect#MYSQL[]
|MySQL 5.5 or above

|api:data.model.query.builder.sql.Dialect#POSTGRES[]
|Postgres 9.5 or above

|api:data.model.query.builder.sql.Dialect#SQL_SERVER[]
|SQL Server 2012 or above

|api:data.model.query.builder.sql.Dialect#ORACLE[]
|Oracle 12c or above

|api:data.model.query.builder.sql.Dialect#SQLITE[]
|SQLite (requires `io.micronaut.sql:micronaut-jdbc-sqlite`)
|===

IMPORTANT: To use SQLite, add the dependency `io.micronaut.sql:micronaut-jdbc-sqlite`, which adds the https://github.com/xerial/sqlite-jdbc[SQLite JDBC Driver] and configures a custom api:data.connection.ConnectionCapabilities[] implementation.

IMPORTANT: The dialect setting in configuration does *not* replace the need to ensure the correct dialect is set at the repository. If the dialect is H2 in configuration, the repository should have `@JdbcRepository(dialect = Dialect.H2)` / `@R2dbcRepository(dialect = Dialect.H2)`. Because repositories are computed at compile time, the configuration value is not known at that time.

=== Tracing calls from Java to Oracle Database sessions

Specify the configuration property `datasources.<datasource-name>.enable-oracle-client-info=true` on a per datasource basis to link database sessions with Java thread activity. By default, this will set:

- The value of `micronaut.application.name` as the `CLIENTID`.
- The class/interface name of the repository as the `MODULE`, potentially with the package name shortened.
- The method name from the repository as the `ACTION`.
- The JVM thread name as the `CLIENT_INFO`.

This metadata appears in the `V$SESSION` view and can be used to figure out what a thread is doing inside the database. The following query is useful to see what SQL is executing:

[source,sql]
----
SELECT
    s.sid,
    s.serial#,
    s.client_identifier as app_name,
    s.client_info as thread_name,
    s.module as repository_name,
    s.action as repository_method,
    q.sql_text,
    s.event,
    s.wait_time,
    s.seconds_in_wait
FROM v$session s
LEFT JOIN v$sql q ON s.sql_id = q.sql_id
WHERE s.username = USER
----

You can control the values of `ACTION`, `MODULE`, `CLIENTID` and `CLIENT_INFO` with the ann:data.connection.annotation.ClientInfo[] annotation on repositories. Note that the ann:data.connection.annotation.ClientInfo.Attribute[] annotation can be used on either the class or the method, thus allowing customization of the  module or action individually. You should prefix the key with `OCSID.` e.g. `OCSID.ACTION` when setting client info this way. Oracle imposes a maximum length of 64 characters for these values, therefore thread, class and method names may be shortened or truncated to fit.

TIP: See the guide for https://guides.micronaut.io/latest/micronaut-data-jdbc-repository.html[Access a Database with Micronaut Data JDBC] to learn more.
