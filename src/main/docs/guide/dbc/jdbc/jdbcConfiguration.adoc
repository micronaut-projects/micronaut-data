=== JDBC driver

Micronaut Data JDBC requires that an appropriate `java.sql.DataSource` bean is configured.

You can either do this manually or use the https://micronaut-projects.github.io/micronaut-sql/latest/guide/#jdbc[Micronaut JDBC] module which provides out-of-the-box support for configuring connection pooling with either Tomcat JDBC, Hikari, Commons DBCP or Oracle UCP.

=== SQL Logging

You can enable SQL logging by enabling trace logging for the `io.micronaut.data.query` logger. For example in `logback.xml`:

.Enabling SQL Query Logging
[source,xml]
----
<logger name="io.micronaut.data.query" level="trace" />
----

With Oracle, the logger also writes the SQL ID of each statement that Micronaut Data JDBC prepares, including `RETURNING` statements, upserts and `@Procedure` calls, at debug level, for example `Oracle SQL ID: 6973n8gn5dwvt`. Use it to find the statement in `V$SQL`, AWR or SQL Monitor reports. The SQL ID needs the Oracle JDBC driver 23 or later; with an older driver, it isn't logged.

In order to validate mapped entities against current schema state set `schema-generate=validate` in the configuration.
If mapped entity does not have corresponding table in the schema or some field does not have column in the database table or
types are not matching then the application will report an error and stop.

==== Schema Contributors

Schema generation creates a table for each entity. To add other database objects to the generated schema, such as views, domains or queues, or to generate the schema of some entities yourself, register a bean that implements api:data.jdbc.config.JdbcSchemaContributor[], or api:data.r2dbc.config.R2dbcSchemaContributor[] for <<r2dbcConfiguration, R2DBC schema generation>>. A contributor that applies to both drivers implements both. The following contributor creates a view over the `book` table:

snippet::example.BookTitlesViewContributor[project-base="doc-examples/jdbc-example", source="main", tags="contributor"]

<1> The bean implements `JdbcSchemaContributor`, the api:data.runtime.schema.SchemaContributor[] of JDBC schema generation.
<2> Contributors are called for every data source with schema generation enabled. The api:data.runtime.schema.SchemaContext[] gives the data source name, dialect, target dialect version, schema generation mode and entities, so a contributor can decide whether it applies.
<3> Create statements run after the tables are created.
<4> With `create-drop`, drop statements run before the tables are dropped, so they drop objects over the tables, such as views. Use `IF EXISTS`, as the object may not exist yet: a failed statement is logged as a warning.

A contributor can also return statements from `buildBeforeTablesStatements`, which run before the tables are created, such as the domains the tables use. With `create-drop`, it drops those objects with `buildBeforeTablesDropStatements`, which runs after the tables are dropped, so a changed domain is created again. Drop statements run in reverse contributor order, since a later contributor's objects can depend on an earlier one's. And it can take over entities with `selectEntities`: the schema generator leaves the selected entities out of the tables it creates, drops and validates, and the contributor builds their schema instead. Micronaut Data's graph support uses this to create the vertex and edge tables and the property graphs of graph entities. Contributors run in `Ordered` order. A failed statement is logged as a warning, as for the generated tables, and statements can contain property placeholders. The schema contributor API is experimental in 5.3.0.

=== Setting the Dialect

As seen in the configuration above you should also configure the dialect. Although queries are precomputed in the repository some cases (like pagination) still require the dialect to specify. The following table summarizes the supported dialects:

.Supported JDBC / R2DBC Dialects
[cols=2*]
|===
|*Dialect*
|*Description*

|api:data.model.query.builder.sql.Dialect#H2[]
|The H2 database (typically used for in-memory testing)

|api:data.model.query.builder.sql.Dialect#MYSQL[]
|MySQL 5.5 or above

|api:data.model.query.builder.sql.Dialect#POSTGRES[]
|Postgres 9.5 or above

|api:data.model.query.builder.sql.Dialect#SQL_SERVER[]
|SQL Server 2012 or above

|api:data.model.query.builder.sql.Dialect#ORACLE[]
|Oracle 19c or above. Generated SQL targets 19c by default; to use 23ai and later features such as the native `BOOLEAN` type, set the dialect version as described in <<sqlOracleBoolean, Oracle BOOLEAN>>

|api:data.model.query.builder.sql.Dialect#SQLITE[]
|SQLite (requires `io.micronaut.sql:micronaut-jdbc-sqlite`)
|===

IMPORTANT: To use SQLite, add the dependency `io.micronaut.sql:micronaut-sql-sqlite`, which adds the https://github.com/xerial/sqlite-jdbc[SQLite JDBC Driver] and configures a custom api:data.connection.ConnectionCapabilities[] implementation.

IMPORTANT: The dialect setting in configuration does *not* replace the need to ensure the correct dialect is set at the repository. If the dialect is H2 in configuration, the repository should have `@JdbcRepository(dialect = Dialect.H2)` / `@R2dbcRepository(dialect = Dialect.H2)`. Because repositories are computed at compile time, the configuration value is not known at that time.

=== Read-only connections and performance

A repository method called outside of a transaction or a connection scope (ann:data.connection.annotation.Connectable[]) obtains a connection from the pool for that single operation. Since 5.3.0, such a connection is used as configured by the pool: Micronaut Data no longer switches it to read-only for read operations.

Toggling the read-only flag is not free. Depending on the driver, `Connection.isReadOnly()` and `Connection.setReadOnly(boolean)` each result in a database round trip, and the flag must be restored before the connection is returned to the pool. With MySQL Connector/J's default settings, a simple query costs four round trips instead of one, which significantly reduces throughput when database latency dominates.

The read-only flag is still applied when you ask for it explicitly, for example with `@Transactional(readOnly = true)`, `@ReadOnly`, `@Connectable(readOnly = true)` or `executeRead` on api:transaction.TransactionOperations[] / api:data.connection.ConnectionOperations[]. Running a group of reads in one transaction or connection scope is cheaper than letting each read obtain its own connection. A read-only transaction applies the flag once when it begins. Inside a read-only connection scope (`@Connectable(readOnly = true)` or `executeRead` on api:data.connection.ConnectionOperations[]), each repository call checks the connection's read-only state with `Connection.isReadOnly()`, which is one round trip per call with MySQL Connector/J's default settings; adding `useLocalSessionState=true` to the JDBC URL avoids it.

To restore the previous behaviour, enable `read-only-connection-per-operation` for a datasource:

[configuration]
----
datasources:
  default:
    read-only-connection-per-operation: true
----

The effect of the read-only flag depends on the driver:

[cols="1,3"]
|===
|Database |Behaviour

|MySQL / MariaDB
|Sets the session read-only, so writes fail. By default the MySQL driver queries the server for `isReadOnly()` and sends `SET SESSION TRANSACTION READ ONLY/WRITE` on every change. Adding `useLocalSessionState=true` to the JDBC URL lets the driver track the session state locally and skip the redundant round trips.

|PostgreSQL
|With the driver's default `readOnlyMode=transaction`, the flag only takes effect in transactions, where writes fail. `readOnlyMode=always` also applies it to auto-commit connections.

|Oracle
|A hint to the driver; writes are not rejected. To reject them, call `setEnforceReadOnly(true)` on api:transaction.jdbc.DataSourceTransactionManager[], which runs `SET TRANSACTION READ ONLY` at the start of read-only transactions.

|SQL Server
|Ignored by the driver; `isReadOnly()` always returns `false`.

|H2
|`setReadOnly` is ignored by the driver; `isReadOnly()` reflects only the database mode, for example `true` when the database is opened with `ACCESS_MODE_DATA=r`.
|===

Read-only connections are also used by some drivers and proxies (for example, the AWS Advanced JDBC Wrapper) and routing data sources to send queries to read replicas. Use explicit read-only transactions or `read-only-connection-per-operation` to keep that routing for non-transactional reads.

==== Oracle True Cache

https://docs.oracle.com/en/database/oracle/oracle-database/26/odbtc/[Oracle True Cache] is a read-only, in-memory cache of a primary database. With the `oracle.jdbc.useTrueCacheDriverConnection` connection property, the Oracle JDBC driver sends the work of a read-only connection to the True Cache and the rest to the primary database. Micronaut Data marks a connection read-only only when you ask for it, so True Cache serves:

- read-only transactions: `@Transactional(readOnly = true)`, `@ReadOnly` or `executeRead` on api:transaction.TransactionOperations[]
- read-only connection scopes: `@Connectable(readOnly = true)` or `executeRead` on api:data.connection.ConnectionOperations[]
- every read outside a transaction, when `read-only-connection-per-operation` is enabled

[configuration]
----
datasources:
  default:
    url: jdbc:oracle:thin:@primary-host:1521/sales
    read-only-connection-per-operation: true
    data-source-properties:
      oracle.jdbc.useTrueCacheDriverConnection: true
----

`data-source-properties` passes the property with Hikari; with other pools, use their connection properties, for example `connection-properties: oracle.jdbc.useTrueCacheDriverConnection=true` with Tomcat JDBC. The driver uses Oracle UCP for True Cache connections, so `com.oracle.database.jdbc:ucp11` (or `ucp17`) must be on the classpath whatever the connection pool. The database service must have a True Cache: otherwise every connection fails with `ORA-18720: True Cache service is not configured on the database`.

True Cache can return slightly stale data, so keep reads that must see the latest writes in read-write transactions.

==== R2DBC

Micronaut Data R2DBC begins read-only transactions (`@Transactional(readOnly = true)` and `executeRead`) with the R2DBC read-only attribute. Oracle R2DBC (`SET TRANSACTION READ ONLY`), R2DBC PostgreSQL (`BEGIN READ ONLY`) and the MySQL and MariaDB drivers (`START TRANSACTION READ ONLY`) then reject writes in them, including writes in a read-write transaction that joins an outer read-only one and `SELECT ... FOR UPDATE`. The SQL Server and H2 drivers ignore the attribute.

On Oracle this is stricter than JDBC: a JDBC read-only transaction commits writes unless `enforceReadOnly` is set, while an R2DBC one rejects them with `ORA-01456`. R2DBC connections outside a transaction are not marked read-only, and Oracle True Cache routing requires JDBC.

=== Batch inserts with generated identifiers

`saveAll` and `insertAll` insert their entities with one JDBC batch when the dialect and driver can return the generated identifier of every row. Otherwise, each entity is inserted with its own statement.

With Oracle, entities with a generated identifier, such as the default `@GeneratedValue` sequence or an `IDENTITY` column, are inserted with one batch when the Oracle JDBC driver is version 23 or later, which returns the generated keys of a batch, also when connected to an older database server. With an older driver, each entity is inserted with its own statement. Entities with an assigned identifier are always batched.

Inserts through a JSON relational duality view (`@JsonView`) are still done one entity at a time: they run as a PL/SQL block with OUT parameters, which the Oracle JDBC driver can't batch.

=== Tracing calls from Java to Oracle Database sessions

Specify the configuration property `datasources.<datasource-name>.enable-oracle-client-info=true` on a per datasource basis to link database sessions with Java thread activity. By default, this will set:

- The value of `micronaut.application.name` as the `CLIENTID`.
- The class/interface name of the repository as the `MODULE`, potentially with the package name shortened.
- The method name from the repository as the `ACTION`.
- The JVM thread name as the `CLIENT_INFO`.

This metadata appears in the `V$SESSION` view and can be used to figure out what a thread is doing inside the database. The following query is useful to see what SQL is executing:

[source,sql]
----
SELECT
    s.sid,
    s.serial#,
    s.client_identifier as app_name,
    s.client_info as thread_name,
    s.module as repository_name,
    s.action as repository_method,
    q.sql_text,
    s.event,
    s.wait_time,
    s.seconds_in_wait
FROM v$session s
LEFT JOIN v$sql q ON s.sql_id = q.sql_id
WHERE s.username = USER
----

You can control the values of `ACTION`, `MODULE`, `CLIENTID` and `CLIENT_INFO` with the ann:data.connection.annotation.ClientInfo[] annotation on repositories. Note that the ann:data.connection.annotation.ClientInfo.Attribute[] annotation can be used on either the class or the method, thus allowing customization of the  module or action individually. You should prefix the key with `OCSID.` e.g. `OCSID.ACTION` when setting client info this way. Oracle imposes a maximum length of 64 characters for these values, therefore thread, class and method names may be shortened or truncated to fit.

TIP: See the guide for https://guides.micronaut.io/latest/micronaut-data-jdbc-repository.html[Access a Database with Micronaut Data JDBC] to learn more.


=== Request boundaries

Set `datasources.<datasource-name>.request-boundaries=true` to mark a request boundary around each connection that Micronaut Data opens, with the JDBC `Connection.beginRequest()` and `Connection.endRequest()` methods. This covers connections opened for connection operations and for transactions (`@Transactional` or `TransactionOperations`). The request begins when the connection is opened, before Micronaut Data applies its read-only or transaction settings. It ends before the connection is closed, after the transaction has committed or rolled back and those settings have been restored. A connection reused by a nested operation or a repository call stays in the request of the scope that opened it.

[configuration]
----
datasources:
  default:
    request-boundaries: true
----

Request boundaries tell the driver where a unit of work starts and ends. Oracle uses them for Transparent Application Continuity, to reset the session state when a request ends (`RESET_STATE`), and to release a Database Resident Connection Pooling (DRCP) server between requests. For a DRCP-enabled Oracle connection, Micronaut Data also releases the pooled server after each request with `detachServerConnection`, even when ending the request fails. DRCP needs this with connection pools other than Oracle UCP. A released connection attaches to a server again on its next round trip. The Oracle JDBC driver can also attach and release the server in `beginRequest()` and `endRequest()` itself; see its `oracle.jdbc.DRCPMultiplexingInRequestAPIs` connection property. Oracle UCP marks request boundaries itself, and nested boundaries are ignored, so the setting is harmless with UCP.
