Micronaut Data JDBC lets an application react to committed database changes through
ann:data.jdbc.annotation.ChangeListener[]. Oracle and PostgreSQL share the listener contract described below;
the available notification capabilities and database setup differ.

See <<oracleQueryNotifications, Oracle Change Notifications>> or
<<postgresChangeNotifications, PostgreSQL Change Notifications>> for prerequisites, examples, and configuration.

[[notificationListenerRequirements]]
== Declaring a Listener

The listener must be a Micronaut bean and must be proxyable; in particular,
do not declare the listener class or listener method `final`.
Micronaut Data validates the listener contract at compilation time. A method annotated with
ann:data.jdbc.annotation.ChangeListener[] must:

* be a non-private, non-static instance method;
* return `void`;
* declare exactly one `ChangeEvent<E>` parameter; and
* use a concrete Micronaut Data persistent entity type for `E`.

The listener uses the `default` datasource unless another datasource is specified through the `dataSource`
attribute, for example `@ChangeListener(dataSource = "inventory")`.
Also declare the database-specific notification annotation described in the Oracle or PostgreSQL section.

[[notificationChangeEvents]]
== Handling Change Events

api:data.jdbc.notification.ChangeEvent[] provides:

* `operation()` -- the api:data.jdbc.notification.ChangeOperation[] reported for the event;
* `entity()` -- the current entity state, when it is available; and
* `metadata(Class)` -- provider-specific metadata, when it is available.

Handle `INVALIDATE` by refreshing the affected application state, for example by reloading a cache or rerunning
a query. An invalidation does not identify an individual changed row. Check whether metadata is present before
accessing it; the database-specific sections describe the available metadata and invalidation conditions.

[[notificationEntityLoading]]
=== Entity Loading

For `INSERT` and `UPDATE`, Micronaut Data reloads and maps the complete entity before invoking the listener.
The entity reflects database state at reload time. It does not represent a historical snapshot of the commit
that produced the notification. Another transaction can change or delete the row before it is loaded.
If no row is found, `entity()` is empty, even for an insert or update event.

For `DELETE` and `INVALIDATE`, `entity()` is empty. Use the database-specific metadata, when available,
to identify a deleted row, and refresh the affected application state for an invalidation.
The Oracle and PostgreSQL sections describe which identifiers are available and how they are used to reload entities.

[[notificationDeliveryAndConcurrency]]
== Delivery and Concurrency

Entity loading and listener methods run on Micronaut's blocking executor. Multiple calls to the same listener
can run concurrently, and their execution and completion order are not guaranteed. Protect shared state, such
as an application cache, against concurrent access and updates arriving in a different order. This includes
processing individual row changes while an `INVALIDATE` callback refreshes the same state.
The database-specific sections describe any additional ordering rules and work limits.

Notifications describe committed database changes and are not part of the transaction that caused them.
Rolled-back changes produce no change notifications. Use notifications to refresh application state or maintain
caches. The API does not provide an audit record of every write, durable consumption, automatic redelivery,
or event identifiers suitable for generic deduplication. Listener code should tolerate repeated observations
and refresh its state when an invalidation or an application-specific consistency check requires it.

Micronaut's blocking executor configuration affects callback concurrency and acceptance. For ongoing subscriptions,
if the executor rejects a data notification, individual change events can be missed. Micronaut Data then retries
submitting an `INVALIDATE` event so the listener can refresh its state. Repeated missed notifications are combined
into one pending invalidation. Submission is retried until accepted or shutdown begins. Changes missed after the
listener starts processing that invalidation can cause an additional invalidation. This refresh does not replay
the missed row notifications. If another delivery attempt cannot be scheduled, Micronaut Data logs an error and
cannot guarantee delivery of the invalidation. Implement `INVALIDATE` handling even if your listener normally
processes individual rows.

[[notificationTransactionsAndRetries]]
== Transactions, Retry, and Recovery

An ann:transaction.annotation.Transactional[] listener executes in a new transaction. It cannot participate in
or roll back the original database transaction because that transaction has already committed before the
notification is delivered.

ann:retry.annotation.Retryable[] and ann:retry.annotation.Recoverable[] can be applied to the listener method.
ann:retry.annotation.Retryable[] applies to both loading the changed entity and executing the listener method:

* if loading an inserted or updated row fails, loading can be retried;
* if loading succeeds but listener code fails, later attempts reuse the entity already loaded for that event; and
* if the method is transactional, each retry attempt runs in a new transaction and a failed attempt is rolled back before the next attempt.

Because a callback can run more than once, listener work should be idempotent. A recovery method can handle a failure
after all retry attempts are exhausted, but recovery does not replay the database notification or restore the
transaction that caused it. Database connection and registration recovery are configured separately in the
Oracle and PostgreSQL sections.

[[notificationCallbackFailures]]
== Callback Failures

If entity loading or listener execution fails and retry or recovery advice does not handle the failure,
Micronaut Data logs it asynchronously with the listener method, operation, and available database-specific
context. The failure is not returned to the database, does not roll back the original change, and does not
trigger automatic redelivery. Subsequent notifications continue to be processed.

If the listener is transactional, its own failed transaction can still be rolled back as described in
<<notificationTransactionsAndRetries, Transactions, Retry, and Recovery>>.
