PostgreSQL notifications provide experimental table-change subscriptions with primary-key metadata and entity loading.
Notifications use one dedicated, non-pooled connection per participating datasource for PostgreSQL `LISTEN`.
The PostgreSQL JDBC driver and a Micronaut `JsonMapper` implementation must be available in the application.

The PostgreSQL contract uses ann:data.jdbc.annotation.ChangeListener[] together with
ann:data.jdbc.annotation.PostgresChangeNotification[]. Its required `channel` member names the exact channel used by
the table triggers. Supply the case-sensitive channel name without SQL identifier quotes, using at most 63 UTF-8 bytes.
Blank names and names containing NUL characters are rejected during compilation.

== Installing the Trigger Function

The `micronaut-data-jdbc` artifact includes this SQL resource:

[source,text]
----
io/micronaut/data/jdbc/notification/postgres/create-notification-function.sql
----

Load this classpath resource from an application database migration and execute it on the migration connection,
selecting the installation schema explicitly. The runnable example below uses Liquibase `sqlFile` to load it directly
from the dependency JAR. Flyway users can load the resource in a Java migration or copy the SQL into a versioned migration.
It creates `micronaut_data_notify_change()` in the migration's current schema and executes with the caller's privileges.
At execution time its search path is restricted to `pg_catalog`. Qualify the function name when creating triggers.
The framework does not install or remove the function or triggers on application startup or shutdown.

For example, after installing the function in `public`, register changes to an existing `public.book` table:

[source,sql]
----
CREATE TRIGGER book_changes
AFTER INSERT OR UPDATE OR DELETE ON public.book
FOR EACH ROW EXECUTE FUNCTION public.micronaut_data_notify_change('book_changes', 'id');

CREATE TRIGGER book_truncate
AFTER TRUNCATE ON public.book
FOR EACH STATEMENT EXECUTE FUNCTION public.micronaut_data_notify_change('book_changes', 'id');
----

The first argument is the channel. Subsequent arguments are the exact mapped primary-key column names.
Supply every component for composite keys, for example `'book_changes', 'tenant_id', 'book_id'`.
These names refer to database columns, including their case, rather than Java properties.
The migration must supply the actual primary key: the function validates column values, but does not inspect primary-key constraints.

Keys must be non-null values represented by PostgreSQL JSON strings, numbers, or booleans.
Missing columns, duplicate column arguments, null keys, and structured JSON keys cause the modifying statement to fail explicitly.
The function supports `AFTER ROW` insert/update/delete triggers and `AFTER STATEMENT` truncate triggers.
Database DDL changes such as dropping a table are outside this trigger protocol.

== Declaring a Listener

[source,java]
----
@Singleton
class BookListener {
    @ChangeListener
    @PostgresChangeNotification(channel = "book_changes")
    void changed(ChangeEvent<Book> event) {
        // INSERT/UPDATE: event.entity() contains the current row, if it still exists.
        // DELETE: identify the removed row using PostgresChangeEventMetadata.oldKeys().
        // INVALIDATE: reload the application's cached state.
    }
}
----

Use `@ChangeListener(dataSource = "inventory")` to select a named datasource.
Use application migrations to create the entity's mapped table and notification triggers.
The mapped schema and table name are read from Micronaut Data's entity metadata.
Startup and reconnection do not query the database catalogs to resolve or validate the mapped table.
Application migrations are responsible for the primary-key constraints and notification triggers.
The provider does not inspect those constraints or triggers at startup or reconnection.
Missing triggers do not fail startup; changes without a publishing trigger produce no notifications.
Missing tables do not fail startup but cause entity loading to fail if a matching insert or update notification is received.
Incoming payloads and their key-column names are validated before entity loading.

Notifications are matched by channel and mapped table name. If the entity mapping specifies a schema,
that schema must also match. Without an explicit schema, notifications from tables with the same name
in different schemas can reach the same listener when they publish to its channel.
Entity loading follows the datasource's schema search path, which may resolve to a different table
from the notification's source. This can load an unrelated row with the same primary key or find no row.
Specify a schema, such as `@MappedEntity(value = "book", schema = "public")`, or use separate channels
for tables in different schemas to avoid this ambiguity.
Identifier matching assumes a UTF-8 database and PostgreSQL's default 63-byte identifier limit.
Quoted mapped identifiers retain their case; unquoted identifiers fold only ASCII `A`–`Z` to lower case.
Both are truncated to 63 UTF-8 bytes without splitting a character, matching PostgreSQL's catalog names.
Supply these actual catalog column names as the trigger's primary-key arguments.

This implementation supports ordinary tables on PostgreSQL 11 or later, with scalar or composite primary keys,
including embedded keys. Key values must be convertible from PostgreSQL's JSON text representation to the mapped
Java key type using Micronaut's conversion service. Association keys and keys with custom converters are unsupported.
Entity filters requiring extra query parameters are rejected at compilation.
This is a table subscription; it does not evaluate arbitrary SQL query-result changes.

== Connections and Dispatch

The listener opens one long-lived, non-pooled physical connection per subscribing datasource using
PostgreSQL's `PGSimpleDataSource`. This connection does not consume a slot in the application connection pool.
Entity loading and application queries continue to use the configured datasource pool. Allow capacity on the
PostgreSQL server for the additional notification connections.

The notification connection factory reuses the named datasource's JDBC URL, username, and password. It also reads
PostgreSQL driver properties from `datasources.<name>.data-source-properties`, `db-properties`, and the
semicolon-separated `connection-properties` setting. Properties embedded in the JDBC URL take precedence.
It lazily creates and caches one `PGSimpleDataSource` per datasource name, capturing these settings on first use.
Each connection attempt opens a new physical connection from the cached source.
Pool settings and connection initialization SQL do not apply to notification connections. Put any required session
settings in PostgreSQL driver properties, such as `currentSchema` or `options`.

The subscription owns each notification connection and closes it after failure or shutdown.
Reconnection opens a new connection from the cached source.

Use a direct PostgreSQL connection or a proxy with session pooling; transaction pooling cannot preserve `LISTEN`
state. Dedicated notification connections use finite PostgreSQL driver timeouts: `connectTimeout` defaults
to 10 seconds, while `loginTimeout` and `socketTimeout` default to 30 seconds. These defaults replace absent
or zero (unlimited) values after JDBC URL properties have been applied. Positive configured values are
preserved; invalid values fail subscription startup. Set these driver properties in the datasource settings
or JDBC URL to suit your deployment. The defaults apply only to notification connections.

`connectTimeout` bounds each socket connection attempt, `loginTimeout` bounds the caller's wait for
connection establishment, and `socketTimeout` bounds socket reads during operations such as `LISTEN`.
These settings do not provide immediate shutdown cancellation or an overall shutdown deadline.
Timed notification polling continues to use `poll-timeout`.

Each notification is submitted directly to Micronaut's blocking executor. Callbacks for the same listener
can run concurrently, and callback execution and completion order are not guaranteed. Listener implementations
must coordinate shared state and tolerate callbacks completing in a different order from notification reception.
Invocation uses the listener bean's interceptors, including `@Retryable`. Insert and update entity loading occurs
inside that invocation, so loading failures can also be retried. Once retries are exhausted, the failure is logged
and subsequent notifications continue.

The provider sends `INVALIDATE` after each successful reconnection, allowing listeners to reconcile
changes missed while disconnected. It reconnects with exponential backoff. An invalid payload invalidates listeners
on its channel. A mismatched key mapping invalidates the affected listener. Well-formed events for other tables
are ignored.

Pending work and executor capacity are controlled by the blocking executor configuration. If the executor rejects
a submission, the dispatcher retains one pending `INVALIDATE` and retries its submission until accepted or shutdown
starts. Lost notifications while an invalidation is pending are covered by that refresh; losses after it starts
request another invalidation. The scheduler only retries submission; callbacks run on the blocking executor.
Recovery, rejected-submission, and malformed-payload invalidations have no PostgreSQL event metadata.
Shutdown stops reception, removes subscriptions, releases the connection, and waits for running callbacks.
Callbacks submitted to the executor that have not started when shutdown begins are discarded.
Context shutdown events and bean destruction initiate cleanup asynchronously. Graceful shutdown returns a stage
that completes when cleanup and running callbacks finish; Micronaut's graceful shutdown configuration controls
how long the application waits.

[configuration]
----
micronaut:
  data:
    jdbc:
      notifications:
        postgres:
          poll-timeout: 1s
          max-retries: -1
          retry-delay: 1s
          retry-delay-multiplier: 2
          max-retry-delay: 60s
----

These settings apply to all subscribing datasources.
Durations must be at least one millisecond and no greater than 2,147,483,647 milliseconds.

`max-retries` defaults to `-1`, which retries recovery until shutdown. Non-negative values count retries
after the initial recovery attempt; `0` allows only that initial attempt. The first recovery attempt waits
for `retry-delay`. Subsequent delays are multiplied by `retry-delay-multiplier`.
All delays, including the initial delay, are capped at `max-retry-delay`.
The multiplier must be an integer of at least `1`; `1` uses a fixed delay.
A successful reconnection resets the retry count and delay. These settings do not retry failed application startup
or listener callbacks. If a finite retry limit is exhausted, the provider logs an error and stops receiving
notifications for that datasource until the application restarts.

== Version 1 Payload

The PostgreSQL notification envelope supplies the channel separately. Its payload is a JSON object:

[source,json]
----
{
  "version": 1,
  "schema": "public",
  "table": "book",
  "operation": "UPDATE",
  "oldKeys": { "id": "9007199254740993" },
  "newKeys": { "id": "9007199254740994" }
}
----

All key values are JSON strings, including numeric and boolean identifiers, so numeric precision is preserved.
Schema, table, and key names retain their database spelling. Payloads contain keys only, with no complete row state.

[cols="1,2,2",options="header"]
|===
|Operation |`oldKeys` |`newKeys`
|`INSERT` |Empty object |Inserted primary key
|`UPDATE` |Previous primary key |Current primary key
|`DELETE` |Deleted primary key |Empty object
|`INVALIDATE` |Empty object |Empty object
|===

Updates retain both keys even when their values are identical. Truncation sends `INVALIDATE`.
If the serialized payload reaches 8,000 bytes in the database encoding, the function emits `INVALIDATE` with the
schema and table identity and empty key objects, keeping the notification below PostgreSQL's default payload limit.
Consumers must validate the protocol version and table/key mapping before loading an entity.

api:data.jdbc.notification.postgres.PostgresChangeEventMetadata[] exposes the channel, schema, table,
and immutable `oldKeys` and `newKeys` maps. A deleted row can be identified from its old keys without reloading it.
Entity loading returns current state at reload time; it cannot reconstruct a row's historical state from this payload.

== Delivery Semantics

Notifications are delivered only after the modifying transaction commits; rolled-back changes produce no notifications.
PostgreSQL may coalesce identical channel/payload pairs within a transaction. For example, multiple updates to the same
row with unchanged keys may produce one update notification. This protocol signals changes for reconciliation and cache
maintenance; it does not provide an audit record of every write or replay after a listener disconnects.

Notifications are visible to all users in the database. Include only appropriate identifiers in payloads;
channels do not provide access control. Trigger execution and PostgreSQL notification-queue failures can fail the write transaction.

See the PostgreSQL link:https://www.postgresql.org/docs/current/sql-notify.html[`NOTIFY` documentation]
for transaction, payload, and delivery behavior.
