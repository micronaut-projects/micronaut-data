Micronaut Data supports geospatial persistence for SQL repositories through the `io.micronaut.data.model.geo` model types:

* api:data.model.geo.Point[]
* api:data.model.geo.MultiPoint[]
* api:data.model.geo.LineString[]
* api:data.model.geo.MultiLineString[]
* api:data.model.geo.Polygon[]
* api:data.model.geo.MultiPolygon[]
* api:data.model.geo.GeometryCollection[]

The implementation is database-aware. Micronaut Data uses attribute converters in the Java model, and then applies dialect-specific SQL functions when reading from or writing to native spatial columns.

=== JSON and WKT converters

The geometry model types in `io.micronaut.data.model.geo` are declared with `@TypeDef(type = DataType.STRING, converter = GeometryJsonConverter.class)`, so GeoJSON is the default mapping.

`GeometryJsonConverter` converts between Micronaut Data geometry objects and GeoJSON strings. `GeometryWktConverter` converts the same model types to and from Well-Known Text (WKT).

Use the default GeoJSON mapping when you want Micronaut Data to serialize geometry values as JSON:

[source,java]
----
@MappedEntity
class GeoEntityJson {

    @Srid(3857)
    @Index(columns = "location")
    @MappedProperty("location")
    private Point point;

    private MultiPoint multiPoint;
}
----

Use `@MappedProperty(converter = GeometryWktConverter.class)` when you want WKT conversion instead:

[source,java]
----
@MappedEntity
class GeoEntityWkt {

    @Srid(3857)
    @Index(columns = "location")
    @MappedProperty(value = "location", converter = GeometryWktConverter.class)
    private Point point;

    @MappedProperty(converter = GeometryWktConverter.class)
    private Polygon polygon;
}
----

SQL Server and PostgreSQL have a geography type in addition to the geometry type. To use the geography type, you must explicitly set it, for example, with `definition = "geography"` or `definition = "geography not null"`:

[source,java]
----
@MappedEntity
class GeoEntityWktGeom {

    @Srid(3857)
    @Index(columns = "location")
    @MappedProperty(value = "location", converter = GeometryWktConverter.class, definition = "geography not null")
    private Point point;
}
----

NOTE: The converter controls the Java-side representation. The generated SQL still uses database-specific spatial functions and native spatial column definitions when the dialect supports them.

=== Database vendor details

Each supported SQL dialect uses its own built-in spatial functions for read and write conversion, generates its own spatial column definitions, and emits its own index DDL.

==== Oracle

Oracle stores spatial values in `SDO_GEOMETRY` columns.

[cols="1,1,1,1"]
|===
| Mapping | Read conversion | Write conversion | Write conversion with SRID

| GeoJSON
| `SDO_UTIL.TO_GEOJSON(column)`
| `SDO_UTIL.FROM_GEOJSON(?)`
| `SDO_UTIL.FROM_GEOJSON(?, NULL, srid)`

| WKT
| `SDO_UTIL.TO_WKTGEOMETRY(column)`
| `SDO_UTIL.FROM_WKTGEOMETRY(TO_CHAR(?))`
| `SDO_UTIL.FROM_WKTGEOMETRY(TO_CHAR(?), srid)`
|===

Spatial indexes are created as Oracle spatial indexes:

[source,sql]
----
CREATE INDEX ... INDEXTYPE IS MDSYS.SPATIAL_INDEX
----

Oracle also requires rows in `USER_SDO_GEOM_METADATA` for spatial columns. Micronaut Data generates those metadata statements automatically during schema creation. The generated metadata depends on the SRID. `@Srid(4326)` uses WGS 84 bounds, `@Srid(3857)` uses Web Mercator bounds, and if no `@Srid` is present but the property is spatially indexed, Micronaut Data defaults metadata generation to SRID `4326`.

Oracle has an additional GeoJSON nuance visible in the geo specs: `SDO_UTIL.FROM_GEOJSON` does not accept `NULL`, and Oracle geometry collections are practically handled as flat collections of primitive elements during GeoJSON conversion rather than nested multi-collection structures.

==== PostgreSQL

PostgreSQL stores spatial values in `GEOMETRY` columns by default.

[cols="1,1,1,1"]
|===
| Mapping | Read conversion | Write conversion | Write conversion with SRID

| GeoJSON
| `ST_AsGeoJSON(column)`
| `ST_GeomFromGeoJSON(?)`
| `ST_SetSRID(ST_GeomFromGeoJSON(?), srid)`

| WKT
| `ST_AsText(column)`
| `ST_GeomFromText(?)`
| `ST_GeomFromText(?, srid)`
|===

Spatial indexes are created with GiST:

[source,sql]
----
CREATE INDEX ... USING GIST (...)
----

PostgreSQL also supports `geography` mappings in the SQL tests. In that case Micronaut Data still uses the same `ST_GeomFromGeoJSON`, `ST_GeomFromText`, `ST_AsGeoJSON`, and `ST_AsText` functions, but casts through `::geography` on writes and `::geometry` on reads because the PostGIS JSON and text conversion functions operate on geometry values.

==== MySQL

MySQL stores spatial values in `GEOMETRY` columns.

[cols="1,1,1,1"]
|===
| Mapping | Read conversion | Write conversion | Write conversion with SRID

| GeoJSON
| `ST_AsGeoJSON(column)`
| `ST_GeomFromGeoJSON(?)`
| `ST_GeomFromGeoJSON(?, 1, srid)`

| WKT
| `ST_AsText(column)`
| `ST_GeomFromText(?)`
| `ST_GeomFromText(?, srid)`
|===

Spatial indexes are created with MySQL spatial index DDL:

[source,sql]
----
CREATE SPATIAL INDEX ...
----

The SQL query builder specs show that MySQL passes SRID directly to the write function instead of wrapping the expression with a separate `ST_SetSRID(...)` call.

==== MariaDB

MariaDB is covered by dedicated geo specs and uses the same converter model as MySQL in Micronaut Data. The generated documentation and SQL function handling follow the same MySQL-style `GEOMETRY` storage model, `ST_AsGeoJSON` and `ST_AsText` read conversion, `ST_GeomFromGeoJSON` and `ST_GeomFromText` write conversion, and `CREATE SPATIAL INDEX ...` DDL.

[cols="1,1,1,1"]
|===
| Mapping | Read conversion | Write conversion | Write conversion with SRID

| GeoJSON
| `ST_AsGeoJSON(column)`
| `ST_GeomFromGeoJSON(?)` or vendor-equivalent MySQL-style GeoJSON function handling
| MySQL-style SRID-aware GeoJSON function handling for the target MariaDB version

| WKT
| `ST_AsText(column)`
| `ST_GeomFromText(?)`
| `ST_GeomFromText(?, srid)`
|===

If you are targeting MariaDB, use the same mapping guidance as MySQL unless your database version introduces different spatial-function behavior.

==== H2

H2 stores spatial values in `GEOMETRY` columns.

[cols="1,1,1,1"]
|===
| Mapping | Read conversion | Write conversion | Write conversion with SRID

| GeoJSON
| `ST_AsGeoJSON(column)`
| `ST_GeomFromGeoJSON(?)`
| `ST_SetSRID(ST_GeomFromGeoJSON(?), srid)`

| WKT
| `ST_AsText(column)`
| `ST_GeomFromText(?)`
| `ST_GeomFromText(?, srid)`
|===

Spatial indexes are created with H2 spatial index DDL:

[source,sql]
----
CREATE SPATIAL INDEX ...
----

The H2 geo specs use H2GIS initialization so that the spatial functions are available in the in-memory test database. That is why the H2 geo configuration includes an `INIT=` clause that loads H2GIS before the tests run.

==== SQL Server

SQL Server defaults generated spatial columns to `GEOGRAPHY`. You can override that with `@MappedProperty(definition = "geometry")` when you want geometry instead.

[cols="1,1,1,1"]
|===
| Mapping | Read conversion | Write conversion | Write conversion with SRID

| GeoJSON
| `column.STAsText()`
| `geography::STGeomFromText(?, srid)` by default, or `geometry::STGeomFromText(?, srid)` for `geometry` columns
| same as write conversion

| WKT
| `column.STAsText()`
| `geography::STGeomFromText(?, srid)` by default, or `geometry::STGeomFromText(?, srid)` for `geometry` columns
| same as write conversion
|===

SQL Server is the special case among the supported vendors because it does not use a built-in GeoJSON read conversion function for the supported mappings.

Spatial indexes are created with SQL Server spatial index DDL:

[source,sql]
----
CREATE SPATIAL INDEX ...
----

When the indexed column definition contains `geometry`, Micronaut Data also appends the geometry grid bounding box clause:

[source,sql]
----
USING GEOMETRY_GRID WITH (BOUNDING_BOX = (-20037508.3427892, -20037508.3427892, 20037508.3427892,  20037508.3427892))
----

That clause is generated for geometry-based SQL Server mappings and is not used for the default `geography` mapping.
