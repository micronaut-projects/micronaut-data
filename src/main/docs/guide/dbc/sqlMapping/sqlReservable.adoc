Micronaut Data JDBC and R2DBC can map Oracle lock-free reservation columns with ann:data.annotation.Reservable[].

Oracle reservable columns are intended for high-concurrency numeric updates where the database tracks reservations without taking row locks for each reservation operation.
Micronaut Data supports schema generation for this feature on Oracle Database 26 and later.

To generate Oracle 26-compatible SQL for Oracle repositories, keep using api:data.model.query.builder.sql.Dialect#ORACLE[] and set the annotation processor option `micronaut.data.sql.dialect-options.oracle.version=26`.
The same value can also be provided as a JVM system property, for example `-Dmicronaut.data.sql.dialect-options.oracle.version=26`.
If both are present, the annotation processor option takes precedence.

The configured dialect `version` is a SQL generation target.
It is not runtime database version detection and it does not inspect JDBC or R2DBC connection metadata.
Use dot-separated numeric notation only, such as `26` or `26.0.0`.

For Gradle Java projects:

[source,groovy]
----
tasks.withType(JavaCompile).configureEach {
    options.compilerArgs.add("-Amicronaut.data.sql.dialect-options.oracle.version=26")
}
----

For Maven projects:

[source,xml]
----
<compilerArgs>
    <arg>-Amicronaut.data.sql.dialect-options.oracle.version=26</arg>
</compilerArgs>
----

The target version can also be set on an individual repository:

[source,java]
----
import io.micronaut.data.jdbc.annotation.JdbcRepository;
import io.micronaut.data.model.query.builder.sql.Dialect;

@JdbcRepository(dialect = Dialect.ORACLE, version = "26")
interface AccountRepository {
}
----

If Micronaut Data schema generation is enabled, configure the same target version on the datasource as well:

[source,yaml]
----
datasources:
  default:
    dialect: ORACLE
    dialect-options:
      version: 26
----

For R2DBC:

[source,yaml]
----
r2dbc:
  datasources:
    default:
      dialect: ORACLE
      dialect-options:
        version: 26
----

IMPORTANT: Repository SQL is generated at compilation time. Datasource configuration is used by runtime components such as schema generation and validation, but it does not change SQL that has already been generated for repository methods. Keep the annotation processor option or repository `version` option aligned with datasource `dialect-options` when using Micronaut Data schema generation.

The ann:data.annotation.Reservable[] annotation can be used on numeric persistent properties.
That includes a scalar property inside an embedded component, but not the embedded association property itself.
It can also be combined with validation annotations to generate Oracle `CHECK` constraints for the reservable column.
Validation annotations without ann:data.annotation.Reservable[] do not create database constraints.

[source,java]
----
import io.micronaut.data.annotation.GeneratedValue;
import io.micronaut.data.annotation.Id;
import io.micronaut.data.annotation.MappedEntity;
import io.micronaut.data.annotation.Reservable;
import jakarta.validation.constraints.PositiveOrZero;

@MappedEntity("account")
public class Account {
    @Id
    @GeneratedValue
    private Long id;

    @Reservable
    @PositiveOrZero
    private Long balance;

    // getters and setters
}
----

The generated Oracle DDL includes the `RESERVABLE` column modifier and, when supported validation annotations are present, a column `CHECK` constraint:

[source,sql]
----
CREATE TABLE "ACCOUNT" (
    "ID" NUMBER(19) NOT NULL,
    "BALANCE" NUMBER(19) RESERVABLE CONSTRAINT "CK_ACCOUNT_BALANCE_GE_0" CHECK ("BALANCE" >= 0) NOT NULL,
    PRIMARY KEY("ID")
)
----

Reservable columns can also be declared without validation annotations.
In that case Micronaut Data generates a reservable column without a `CHECK` constraint.

== Updates

Oracle reservable column updates must be expressed as delta operations, for example `balance = balance + ?` or `balance = balance - ?`, and must identify the primary key in the `WHERE` clause.
Oracle does not allow mixing reservable and non-reservable column assignments in the same update statement.
Use derived reservation methods to generate reservation-delta updates. A method name starts with `reserve` and declares one or more `Increment<Property>` or `Decrement<Property>` operations joined by `And`.

This `Account` example has no non-reservable mutable properties, so it extends api:data.repository.GenericRepository[] and explicitly declares only the operations it supports.
Entities with at least one non-reservable updatable property can continue to extend api:data.repository.CrudRepository[].

[source,java]
----
import io.micronaut.data.annotation.Id;
import io.micronaut.data.jdbc.annotation.JdbcRepository;
import io.micronaut.data.model.query.builder.sql.Dialect;
import io.micronaut.data.repository.GenericRepository;

@JdbcRepository(dialect = Dialect.ORACLE, version = "26")
interface AccountRepository extends GenericRepository<Account, Long> {

    Account insert(Account account);

    int reserveIncrementAmountAndDecrementBalance(
        @Id Long id,
        Long amount,
        Long balance
    );
}
----

Generated entity update operations skip reservable properties.
For example, `repository.update(account)` updates non-reservable properties but does not assign the reservable column directly.
If an entity has no non-reservable update properties, Micronaut Data fails query generation instead of rendering an invalid update statement.
The same restriction applies to `save(...)` because save can resolve to an update path at runtime.
If an entity's only updateable properties are reservable, generated `save(...)` and `update(...)` methods are unsupported, including inherited methods from api:data.repository.CrudRepository[].
Micronaut Data reports this at compilation time with a message that explains that all updateable properties are reservable.
For those entities, extend api:data.repository.GenericRepository[] and explicitly declare the supported operations, such as `insert(...)`, finder methods, delete methods, and derived reservation methods.
Use `insert(...)` for new rows and an explicit derived reservation method for existing rows.

This restriction is specific to reservable-only update shapes.
If an entity has at least one non-reservable updatable property, generated `save(...)` and `update(...)` methods remain supported and Micronaut Data simply omits reservable properties from the generated `SET` clause.

Each reservation method identifies the row with exactly one `@Id` parameter whose type matches the entity identity. For a composite primary key, use the entity's `@EmbeddedId` value object as that parameter; Micronaut Data expands it into all primary-key columns.
Each operation target must be a numeric ann:data.annotation.Reservable[] scalar property. The delta parameters must have the same names as their reservable properties, and no additional non-ID parameters are allowed. Embedded scalar properties use the flattened property path in the method name and parameter name, for example `reserveDecrementLimitsAvailableBalance(@Id Long id, Long limitsAvailableBalance)`.
Reservation methods cannot target relationship paths. A scalar reservable property inside an embedded component is supported, but `reserveIncrementAccountBalance(...)` is rejected when `account` is a relationship.
Generated reservation updates cannot mix reservable and non-reservable assignments and do not support Oracle DML `RETURNING`.
Criteria API updates of reservable properties are not supported. Use derived reservation methods instead; arbitrary criteria expressions are not validated against Oracle lock-free reservation restrictions.

== Runtime Errors

Reservation updates that fail because of a database integrity constraint, such as a generated reservable `CHECK` constraint, throw api:data.exceptions.DataIntegrityViolationException[].
This applies to JDBC and R2DBC and is not limited to reservable columns. Micronaut Data maps broad SQL integrity failures to that exception type while preserving existing api:data.exceptions.EntityExistsException[] behavior for unique and duplicate-key cases.

This database exception is distinct from Bean Validation failures.
Method or entity validation that fails before SQL execution continues to throw `jakarta.validation.ConstraintViolationException`.

== Restrictions

Micronaut Data validates reservable mappings during schema generation:

* ann:data.annotation.Reservable[] is supported only for Oracle schema generation.
* The configured Oracle dialect option version must be 26 or later.
* The property type must be numeric.
* The entity must have a primary key.
* A reservable property cannot be a primary key, generated value, relationship, foreign key, indexed property, or use a custom column definition.
* An entity can declare at most 10 reservable properties.
* Only column-level check constraints derived from supported validation annotations are generated. Table-level check constraints are not generated.
* Oracle applies additional table-level restrictions, for example on partition keys and some table types such as index-organized, external, temporary, blockchain, and sharded tables. Micronaut Data does not try to detect every database-side table restriction during compile-time schema generation.

Supported validation annotations include `jakarta.validation` and `javax.validation` variants of `Positive`, `PositiveOrZero`, `Negative`, `NegativeOrZero`, `Min`, `Max`, `DecimalMin`, and `DecimalMax`.
