Micronaut Data JDBC and R2DBC can generate the schema of an https://docs.oracle.com/en/database/oracle/oracle-database/26/shard/[Oracle Globally Distributed Database] with ann:data.annotation.Sharded[] and ann:data.annotation.Duplicated[]. A sharded table is partitioned across the shards by consistent hash of its sharding key (system-managed sharding), while a duplicated table is replicated to every shard, so that queries of sharded tables join it locally.

<2> The sharding key defaults to the primary key. Oracle requires the sharding key to be part of the primary key, so the `key` member, which lists the properties of the key, is only needed when the primary key has more columns

With the Oracle dialect, the following tables are generated:

[source,sql]
----
CREATE SHARDED TABLE "SUBSCRIBER" ("SUBSCRIBER_ID" VARCHAR(255) NOT NULL, "NAME" VARCHAR(255) NOT NULL, PRIMARY KEY("SUBSCRIBER_ID"))
    PARTITION BY CONSISTENT HASH ("SUBSCRIBER_ID") PARTITIONS AUTO TABLESPACE SET TS_SUBSCRIBERS

CREATE SHARDED TABLE "SUBSCRIPTION" ("SUBSCRIBER_ID" VARCHAR(255) NOT NULL, "SUBSCRIPTION_NO" NUMBER(19) NOT NULL, "PLAN" VARCHAR(255) NOT NULL, PRIMARY KEY("SUBSCRIBER_ID","SUBSCRIPTION_NO"))
    PARENT "SUBSCRIBER" PARTITION BY CONSISTENT HASH ("SUBSCRIBER_ID") PARTITIONS AUTO TABLESPACE SET TS_SUBSCRIBERS

CREATE DUPLICATED TABLE "PLAN" ("CODE" VARCHAR(255) NOT NULL, "NAME" VARCHAR(255) NOT NULL, PRIMARY KEY("CODE")) TABLESPACE PLANS_TSP
----

The statements must run on the shard catalog, in a session with shard DDL enabled (`ALTER SESSION ENABLE SHARD DDL`), which then creates the tables on the shards. A child table is related to its parent by equi-partitioning (`PARENT`) rather than by a foreign key, since Micronaut Data does not generate foreign keys. Other dialects ignore both annotations and generate plain tables, so that tests can run on H2 or Oracle Free, which cannot host sharded tables. Micronaut Data does not detect whether the database is sharded. Root tables are created before their child tables, and child tables are dropped first.

Indexes of a sharded table are generated as local indexes (`CREATE INDEX ... LOCAL`), since Oracle rejects global indexes on sharded tables.

The build or the schema generation fails if a mapping cannot work on a sharded database:

* The sharding key must be part of the primary key, and the parent must be a sharded root table
* The primary key of a sharded table cannot use an identity column, which Oracle does not allow
* The sharding key cannot use `@GeneratedValue`. The application needs the key to connect to the shard before the insert, so it must assign the value itself
* A unique index must contain the sharding key
* A sharded or duplicated entity cannot have an association that needs a join table

A generated primary key column outside the sharding key, such as an order number of a table sharded by customer, uses a sharded sequence (`CREATE SEQUENCE ... SHARD`), so that its values stay unique when a chunk moves to another shard. For `Long` and `Integer` properties, its `MAXVALUE` is limited to 18 and 9 digits, so that the values fit the column. The shard offset is part of those digits and `NEXTVAL` fails once a value needs more, so an `Integer` id only has between about 100,000 and a million values per shard, depending on the Oracle release. Use `Long` for generated ids of sharded tables. A sequence you create with the `definition` member of `@GeneratedValue` is used as written.

A duplicated table can have an identity column, but rows can then only be inserted through the shard catalog, because Oracle rejects inserts from a shard (`ORA-05156`).

To route the connections of an application to the shard of a sharding key, see the sharding module of https://micronaut-projects.github.io/micronaut-oracledb/latest/guide/[Micronaut Oracle Database].
