Micronaut Data can run full-text searches through repositories: an entity declares which properties are searchable, and repository methods search them and return hits ordered by relevance. The API is the same for every supported store; this section describes the PostgreSQL implementation, which uses the built-in `tsvector` and `tsquery` types.

NOTE: Full-text search is experimental. PostgreSQL and Oracle are supported for JDBC and R2DBC, and MongoDB (`$text` and MongoDB Search) has its own <<mongoTextSearch, section>>.

== Mapping searchable entities

Annotate the entity with ann:data.annotation.search.Searchable[] and the properties to index with ann:data.annotation.search.SearchField[]:

snippet::example.Book[project-base="doc-examples/jdbc-search-example", source="main", tags="entity"]

<1> `language` selects the text search configuration used for stemming and stop words (`english` by default); PostgreSQL passes it to `to_tsvector` and `to_tsquery`.
<2> `weight` makes matches in this property count more in the relevance score; PostgreSQL maps `HIGH`, `MEDIUM`, `LOW` and `LOWEST` to the labels `A` to `D` of `setweight`. `fuzzy` adds a `pg_trgm` GIN index over the column for `SearchFuzzy` queries.
<3> A property without a declared weight is indexed without a label.

A property annotated ann:data.annotation.search.Language[] holds the language of each row, with the entity language as the fallback when it is `null`: PostgreSQL uses it as the text search configuration of the row's `tsvector`, `to_tsvector(mn_regconfig(coalesce(language,'english')), ...)`, in the queries and in the generated index, while the query string keeps the entity language; MongoDB passes it as `language_override`. Oracle, Elasticsearch and OpenSearch ignore it, as their analysis is fixed per index.

With schema generation enabled, Micronaut Data creates a `GIN` expression index over the combined `tsvector` of the search fields, so the generated queries use the index. For a production schema, create the same index with your migration tool; the expression is printed in the generated DDL.

== Searching

A repository that extends api:data.repository.SearchRepository[] searches every `@SearchField` property:

snippet::example.BookService[project-base="doc-examples/jdbc-search-example", source="main", tags="search"]

<1> `search(String)` returns api:data.model.vector.search.SearchResults[], ordered by relevance with the best match first. `search(String, Pageable)` returns one page and orders by the pageable's sort.
<2> Each api:data.model.vector.search.SearchResult[] holds the entity.
<3> The relevance score of the hit. On PostgreSQL it is the `ts_rank_cd` rank. Scores order the results and are not comparable between stores; `SearchResults.maxScore()` helps to normalise them.
<4> `countHits(String)` counts the matches.

The search string uses a portable grammar: words separated by whitespace match any term, `"quoted words"` match a phrase, a leading `-` excludes a term, and `OR` separates alternatives. `bake coffee -cake OR tea` matches rows containing `bake` or `coffee` but not `cake`, or rows containing `tea`. The search string is safe to take from user input: Micronaut Data parses it itself, converts it to the store's query syntax at bind time and binds it as a parameter. The other `SearchQuery` options are not meant for user input: `language` must be a configuration name and is rejected otherwise, `syntax(NATIVE)` passes the store's own syntax through, and `candidates` sizes the hybrid fetch.

== Derived search methods

Search is also available as a keyword in repository method names, with or without a property:

snippet::example.BookRepository[project-base="doc-examples/jdbc-search-example", source="main", tags="repository"]

<1> api:data.repository.SearchRepository[] adds `search` and `countHits`.
<2> `Search` after a property matches any term in that property; `findBySearch(String)` with no property matches every search field.
<3> A method with the `search` prefix that returns `SearchResults` projects the score and orders by it, like a vector search. `SearchAll` requires every term.
<4> `SearchPhrase` requires the terms to be adjacent and in order.
<5> `SearchPrefix` matches every term as a prefix, for search-as-you-type.
<6> Search keywords combine with any other predicate.
<7> A trailing api:data.model.vector.search.Score[] parameter after the predicate parameters keeps only the hits whose relevance score is at least its value, as a restriction rendered by the store (`ts_rank_cd(...) >= ?` on PostgreSQL, `SCORE(n) >= ?` on Oracle, `min_score` on Elasticsearch and OpenSearch, a `$match` on the `searchScore` with MongoDB Search); MongoDB `$text` cannot restrict on the score.
<8> `SearchFuzzy` matches terms with typos; PostgreSQL uses `pg_trgm` word similarity, see the notes below.

|===
|Keyword |Meaning |PostgreSQL query

|`Search` |any term |`to_tsquery('a' \| 'b')`
|`SearchAll` |every term |`to_tsquery('a' & 'b')`
|`SearchPhrase` |adjacent terms, in order |`to_tsquery('a b')`
|`SearchPrefix` |every term as a prefix |`to_tsquery('a:*' & 'b:*')`
|`SearchFuzzy` |edit-distance match |not supported, fails at compile time
|===

On Oracle the same keywords render `CONTAINS` queries: `{a} | {b}`, `{a} & {b}`, `{a b}`, `a% & b%` and `fuzzy(a,60,100)` respectively, so `SearchFuzzy` is available there.

Methods that return `List`, `Page` or a DTO filter by the search without projecting a score. A sort parameter or a `Pageable` replaces the relevance order.

== Programmatic queries

When the fields or the match mode are only known at runtime, build a api:data.model.search.SearchQuery[] and pass it to `search`:

snippet::example.BookService[project-base="doc-examples/jdbc-search-example", source="main", tags="searchQuery"]

<1> The search string, in the same grammar as `search(String)`.
<2> `fields` restricts the search to some of the `@SearchField` properties; without it every search field is searched.
<3> `mode` selects how the terms match: `ANY` (the default), `ALL`, `PHRASE`, `PREFIX` or `FUZZY`, like the `Search`, `SearchAll`, `SearchPhrase`, `SearchPrefix` and `SearchFuzzy` keywords.
<4> `search(SearchQuery)` returns the hits ordered by relevance.
<5> `search(SearchQuery, Pageable)` returns one page; a sort on the pageable replaces the relevance order.

`minScore` restricts the hits to those whose score reaches the threshold, as a predicate the store evaluates (`ts_rank_cd(...) >= ?`, `SCORE(n) >= ?`, `min_score`), so pages are full and `totalHits` counts only the hits above it; MongoDB `$text` cannot restrict on its score and throws api:data.model.search.UnsupportedSearchFeatureException[]. On a hybrid search the threshold compares the fused score instead. A query is compiled at runtime through the same criteria API as a derived method, so a store that lacks the requested mode throws api:data.model.search.UnsupportedSearchFeatureException[] when the method runs rather than at compile time.

`boost(field, factor)` weighs the matches of a property at query time, replacing its `@SearchField(weight)`: Oracle multiplies the field's `SCORE(n)`, Elasticsearch and OpenSearch boost the field (`title^2`) and MongoDB Search sets the operator's `score.boost`; PostgreSQL and MongoDB `$text` throw `UnsupportedSearchFeatureException`. `fuzzy(maxEdits)` selects the `FUZZY` mode with the edit distance: Elasticsearch, OpenSearch and MongoDB Search honour one or two edits (`term~2`, `fuzzy.maxEdits`), Oracle's `fuzzy` operator has a fixed similarity and rejects more than one edit. `language(name)` analyses the query with another text search configuration than the entity's: PostgreSQL passes it to `to_tsvector` and `to_tsquery` in place of `@Searchable(language)`, MongoDB `$text` sets `$language`, and Elasticsearch and OpenSearch analyse the query with the language's analyzer (`simple` disables stemming); Oracle and MongoDB Search, whose analysis is fixed per index, throw `UnsupportedSearchFeatureException`. The criteria API carries all three as api:data.model.search.TextMatchOptions[] on `textMatch`, `searchScore` and `searchHighlight`.

`syntax(SearchSyntax.NATIVE)`, or the `SearchNative` method keyword, passes the search string to the store unparsed instead of the portable grammar: PostgreSQL takes `tsquery` syntax (`programming & !kotlin`), Oracle Text a `CONTAINS` query (`programming NOT kotlin`), MongoDB `$text` its search string (`programming -kotlin`), MongoDB Search a `queryString` operator with the first searched field as `defaultPath`, and Elasticsearch and OpenSearch a `query_string` query over the searched fields. A malformed native query fails at the store, so reserve it for trusted input; the portable grammar escapes what it binds.

snippet::example.BookService[project-base="doc-examples/elasticsearch-search-example", source="main", tags="options"]

<1> A boost of the title above the description, whatever their index weights.
<2> Fuzzy matching with up to two edits per term.

== Highlighting

`highlight` names the properties whose matching terms should be returned wrapped in `<em>` tags:

snippet::example.BookService[project-base="doc-examples/jdbc-search-example", source="main", tags="highlight"]

<1> Each named property must be a `@SearchField`.
<2> `SearchResult.highlights()` maps a property name to its fragments; a property that does not match the query has one fragment without tags on PostgreSQL and Oracle, and none on Elasticsearch and OpenSearch.

A property declared `@SearchField(highlightable = true)` is highlighted by default: a `search` method returning `SearchResults` projects the fragment of every highlightable property it searches, and `SearchQuery.highlight()` without arguments requests the highlightable properties.

The tags are the same on every store, so a client can render them without knowing the backend. PostgreSQL renders `ts_headline`, Oracle `CTX_DOC.POLICY_SNIPPET`, the document stores the `highlight` request clause, and MongoDB Search the `highlight` option of `$search` with the `searchHighlights` metadata. MongoDB `$text` cannot highlight and throws api:data.model.search.UnsupportedSearchFeatureException[]. The criteria API exposes the same projection as `PersistentEntityCriteriaBuilder.searchHighlight(field, query, MatchMode)`.

== Hybrid search

A hybrid search combines the text match with a vector similarity, so a row that is close to a query embedding ranks high even when it shares no words with the query, and a row matching both ranks first. On a store with vector search, pass the vector property and the query vector to the `SearchQuery`:

snippet::example.BookService[project-base="doc-examples/jdbc-search-example", source="main", tags="hybrid"]

<1> The entity's vector property and the query embedding.
<2> Optional weights of the two rankings, `1` by default; `candidates` sets how many hits each ranking contributes, `100` by default.
<3> The score of a hit is its reciprocal rank fusion value: `textWeight / (60 + text rank) + vectorWeight / (60 + vector rank)`, with `rankConstant` replacing `60`.

A derived finder of the form `searchBy[Property]SearchAnd<Vector>Near(String query, Vector vector[, Pageable])`, such as `searchByTitleSearchAndEmbeddingNear`, builds the same `SearchQuery` from its arguments with the default weights. Micronaut Data runs the text query and the nearest-neighbour query, each limited to `candidates` hits, and fuses the two rankings in memory, so hybrid search is available on every store that supports both text and vector search (PostgreSQL with pgvector, Oracle Database 23ai, MongoDB Search, Elasticsearch and OpenSearch), including with a `Pageable`, which cuts the page from the fused ranking. MongoDB Search fuses natively with `$rankFusion` when the query allows it, see the <<mongoTextSearch, MongoDB section>>. A sort on the pageable is rejected because the fused score defines the order; `highlight` applies to the text hits; `minScore` compares the fused score. A store without vector search throws api:data.model.search.UnsupportedSearchFeatureException[].

== Criteria API

The criteria builder exposes the same predicate through `PersistentEntityCriteriaBuilder.textMatch(field, query, MatchMode)` and the score through `searchScore(fields, query, MatchMode)`, so a api:data.repository.jpa.criteria.PredicateSpecification[] can combine a text match with any other restriction.

== PostgreSQL notes

- Queries render `to_tsvector('<language>', <column>) @@ to_tsquery('<language>', ?)` and rank with `ts_rank_cd`; several fields are concatenated with `||`, wrapped in `coalesce` and `setweight` as declared.
- The query parameter is converted to `tsquery` syntax by a parameter converter chosen for the keyword, so the SQL stays the same for every search string.
- Fuzzy matching (`SearchFuzzy`, `SearchQuery.fuzzy`) uses the `pg_trgm` extension: a term matches a field when `word_similarity(term, column)` reaches `pg_trgm.word_similarity_threshold` (`0.6` by default, tunable per session or database), rendered as `mn_term.t <% column` over `unnest(string_to_array(?, ' '))` of the positive terms, with the negated terms excluded by a `NOT EXISTS`. The score is the best `word_similarity` of any term over the fields, multiplied by the weights. The edit distance of `SearchQuery.fuzzy(n)` is not honoured beyond the default. `@SearchField(fuzzy = true)` makes schema generation add `CREATE EXTENSION IF NOT EXISTS pg_trgm` and a `gin_trgm_ops` index over the column; queries run without the index too, scanning the table. Highlights of a fuzzy search mark the terms where they occur literally, through `plainto_tsquery`.
- Query-time boosts are not available.
- Highlights render `ts_headline('<language>', <column>, to_tsquery('<language>', ?), 'StartSel=<em>,StopSel=</em>')`, which returns a fragment of the column with the default `ts_headline` length limits.
- Stemming follows the text search configuration named by `@Searchable(language)`; use `simple` to disable it.

== Oracle notes

- Each search field gets its own Oracle Text `CONTEXT` index, created by schema generation as `CREATE INDEX idx_<table>_search_<column> ON <table> (<column>) INDEXTYPE IS CTXSYS.CONTEXT PARAMETERS ('SYNC (ON COMMIT)')`. The index is synchronised on commit, so rows are searchable as soon as the transaction that wrote them commits. ann:data.annotation.search.OracleTextIndex[]`(parameters)` on the entity replaces the parameters clause, for another sync mode, a lexer, a wordlist or the index memory; it applies to the JSON search index of a JSON entity too.
- A single-field search renders `CONTAINS(<column>, ?, 1) > 0` and ranks with `SCORE(1)`. A search over every search field matches any field with the positive terms and then excludes rows where any field matches a negated term; the score is the sum of the per-field scores multiplied by their numeric weights (`HIGH` 10, `MEDIUM` 5, `LOW` 2, `LOWEST` 1).
- `SearchAll` requires every term within one field. Terms are escaped in braces, so reserved words such as `and` or `or` are matched literally.
- The default lexer matches words literally; there is no stemming unless the index is created with a lexer that enables it. A `@Language` column is ignored.
- Entities stored as a JSON column (`@EntityRepresentation(columnType = JSON)`) get one JSON search index over the column, created by schema generation as `CREATE SEARCH INDEX idx_<table>_search ON <table> (<column>) FOR JSON PARAMETERS ('SYNC (ON COMMIT)')`, and are searched with `CONTAINS(<column>, '(' || ? || ') INPATH (/<property>)', n) > 0`, which ranks with `SCORE(n)` like a relational entity. A JSON search index cannot be created on a JSON-relational duality view, so `@JsonView` entities are not searchable.
- Highlights render `CTX_DOC.POLICY_SNIPPET('MN_SEARCH_POLICY', <column>, ?, starttag => '<em>', endtag => '</em>')` over the column text, or over `JSON_VALUE` for a JSON entity. The `MN_SEARCH_POLICY` Oracle Text policy is created by schema generation with the default lexer; create it in your migrations with `CTX_DDL.CREATE_POLICY('MN_SEARCH_POLICY')`, which needs the `CTXAPP` role.

== Index operations

Schema generation creates the search indexes with the tables. To manage them while the application runs, inject api:data.runtime.search.SearchIndexOperations[]: `exists`, `create`, `drop`, `recreate` and `sync` take the entity class. On a JDBC datasource (one bean per datasource) they run the dialect's DDL, `sync` runs `CTX_DDL.SYNC_INDEX` on Oracle Text and nothing on PostgreSQL, whose GIN indexes are always current. On MongoDB they manage the `$text` index or the search and vector search indexes, and `sync` waits until the search indexes are queryable. On Elasticsearch and OpenSearch the index holds the documents, so `drop` removes them; `sync` refreshes the index. The document stores also take `micronaut.data.search.schema-generate` (`CREATE` by default, `CREATE_DROP` or `NONE`) for the indexes created on startup.

== Capability matrix

The portable API is the same on every store; the table lists which optional capabilities each store honours. A capability a store lacks fails at compile time for a derived method and throws api:data.model.search.UnsupportedSearchFeatureException[] from `search(SearchQuery)`.

An application can check the matrix at runtime before it builds a query: inject api:data.runtime.search.SearchCapabilities[] and call `getSearchCapabilities(entityType)` or `supports(entityType, capability)` with a api:data.model.search.SearchCapability[] value (`PHRASE`, `PREFIX`, `FUZZY`, `FIELD_SCOPE`, `BOOST`, `FUZZINESS`, `HIGHLIGHT`, `LANGUAGE_OVERRIDE`, `MIN_SCORE`, `VECTOR` or `HYBRID`). Each JDBC and R2DBC datasource registers one bean that answers by its dialect, MongoDB answers by whether the entity declares a `@MongoSearchIndex`, and Elasticsearch and OpenSearch answer with the full set. An entity without `@Searchable` reports no capabilities.

|===
|Capability |PostgreSQL |Oracle |MongoDB `$text` |MongoDB Search |Elasticsearch / OpenSearch

|Any, all and negated terms, relevance order |yes |yes |yes |yes |yes
|Phrase (`SearchPhrase`) |yes |yes |yes |yes |yes
|Prefix (`SearchPrefix`) |yes |yes |no |yes |yes
|Fuzzy (`SearchFuzzy`) |yes, `pg_trgm` |yes |no |yes |yes
|Field scope (`findByTitleSearch` searches only `title`) |yes |yes |no, the whole text index |yes |yes
|Index-time weights (`@SearchField(weight)`) |yes |yes |yes |yes, as boosts |yes
|Query-time boosts (`SearchQuery.boost`) |no |yes |no |yes |yes
|Edit distance (`SearchQuery.fuzzy(n)`) |no |no, one edit |no |yes, up to 2 |yes, up to 2
|Highlighting |yes |yes |no |yes |yes
|Vector search and hybrid search |yes, pgvector |yes, 23ai |no |yes, `$vectorSearch`, hybrid fused by `$rankFusion` |yes, `knn`
|Reactive and async repositories |yes |yes |yes |yes |yes
|Minimum score (`Score` parameter) |yes |yes |no |yes |yes
|Per-row language (`@Language`) |yes |no |yes |no |no
|Query language (`SearchQuery.language`) |yes |no |yes |no |yes
|Native syntax (`SearchNative`, `SearchQuery.syntax(NATIVE)`) |`tsquery` |`CONTAINS` query |`$text` string |`queryString` |`query_string`
|===
