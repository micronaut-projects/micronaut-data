Path finders check for paths and count them, with `existsPath` and `countPaths`, and `findAllPaths` returns every path up to the maximum depth, shortest first, on a release whose `GRAPH_TABLE` supports `ONE ROW PER STEP`, such as Oracle AI Database 26ai. Shortest path finders fail at build time, as `GRAPH_TABLE` has no shortest path search. A path takes each relationship once, as in Cypher, and a path over several relationship types names them after `By`, as SQL/PGQ cannot read the label of an edge. `StartsWith`, `EndsWith` and `Contains` are supported through `LIKE`.

Path finders need a maximum depth set with ann:data.graph.annotation.PathLimit[], either on the method or on an `int` parameter, whose argument is capped by `micronaut.data.graph.max-path-depth` as described in <<graphPaths, Paths and Shortest Paths>>. Relationship finders need a single relationship type. An undirected relationship finder returns each relationship with the nodes it starts and ends at as stored in its edge table, whichever argument matched which end, as Neo4j does.

== Writing nodes

A property graph over tables is a view, so its repositories write nodes to their vertex tables with SQL, as Micronaut Data JDBC does. The value of ann:data.graph.annotation.Node[] names the vertex table, and `labels` the label the graph gives it, as in the `Account` entity of the <<graphOracleQuickStart, quick start>>.

Save, update and delete methods, including those of api:data.repository.CrudRepository[], are compiled to SQL for Oracle at build time and run by the JDBC repository operations of the same data source:

snippet::example.BankGraphSpec[project-base="doc-examples/oracle-graph-example", tags="save", indent="0", languages="java,kotlin,groovy,python"]

<1> Runs `INSERT INTO "ACCOUNTS" ("NAME","ID") VALUES (?,?)`.
<2> Runs a SQL/PGQ `GRAPH_TABLE` query over the property graph.

Writes join the current connection and transaction of the data source, as graph queries do. Writes need the `micronaut-data-jdbc` module, which `micronaut-data-oracle-graph` depends on. Saving a node writes only its row: relationships are rows of their edge tables, which a ann:data.jdbc.annotation.JdbcRepository[] over an entity of the edge table writes.

Graph repositories write only the row of a node in its vertex table. A property with ann:data.graph.annotation.Relationship[] has no column there, whether it holds one node or many, so a save or update of a node with a single relationship set, such as a `Person` with its `mentor` set, or with a relationship collection that is not empty, such as an `Account` with `transfers`, fails with a api:data.exceptions.DataAccessException[] before anything is written, rather than losing the relationships. Write the edges through a ann:data.jdbc.annotation.JdbcRepository[] over the entity of the edge table instead, and save the nodes with their relationships null or empty. Nodes read through a graph repository come back with their relationships empty, so they can be saved again.

Methods that return what they write, such as `updateReturning`, run as `RETURNING ... INTO` on the vertex table. A node with a single relationship can only return its properties from them, such as with `updateReturningName`, because the relationship has no column to read: returning the whole entity fails at compile time.

== Generating the schema

When schema generation is enabled for the data source, the JDBC schema generator creates the tables of the graph entities and the property graphs over them, as it does for the tables of Micronaut Data JDBC entities:

[configuration]
----
datasources:
  default:
    schema-generate: CREATE_DROP
----

The tables follow the mapping of the entities:

* Each ann:data.graph.annotation.Node[] entity gets a vertex table named by its ann:data.graph.annotation.Node[] value, with columns for its properties but not for its relationships.
* A relationship to a ann:data.graph.annotation.RelationshipProperties[] entity is stored in the table of that entity, which gets a column referencing the node that owns the relationship, named after the owner, such as `ACCOUNTID`. The ann:data.graph.annotation.TargetNode[] property is the column referencing the other end. The ann:data.graph.annotation.RelationshipId[] is the key of the edge table, so two relationships can link the same pair of nodes, such as a person playing two roles in one movie; the pair of columns is indexed.
* A relationship to a node is stored in an edge table named after the owner's table and the relationship type, such as `MEMBERS_FOLLOWS`, with a column referencing the owner and a column named after the property referencing the target. When the owner has the same type towards several nodes the name also has the target's table, such as `FANS_LIKES_FILMS` and `FANS_LIKES_NOVELS`.
* A relationship declared on both of its nodes, with opposite directions, is one edge table: the table of the relationship entity if one side has one, otherwise the table named after the node the edge leaves. Declare a relationship entity on one side only: a relationship entity on both sides fails the build.
* A table holds one relationship type between one pair of nodes, as nothing in a row tells two relationships apart. Two relationships that need the same table fail the build, such as one relationship entity used for two relationship types, or a node with the same type towards the same node in both directions: give each of them its own relationship entity.

These mappings, and a relationship entity used by several nodes, fail the compilation of an ann:data.oracle.graph.annotation.OracleGraphRepository[] or ann:data.oracle.graph.r2dbc.annotation.OracleGraphR2dbcRepository[] whose entity reaches them through its relationships and relationship entities. The compiler only sees the entities one repository reaches, so the generator checks them again at startup over every node of the data source, and fails for conflicts between entities that only meet in the graph built from several repositories.

Each graph named by an ann:data.oracle.graph.annotation.OracleGraphRepository[] of the data source, or an ann:data.oracle.graph.r2dbc.annotation.OracleGraphR2dbcRepository[] of the connection factory with <<graphOracleR2dbcSchema, R2DBC>>, is then created with `CREATE OR REPLACE PROPERTY GRAPH`, over the vertex tables of the entities its repositories reach through their relationships and the edge tables between them. Incoming relationships are stored as edges from their target to their owner. For the `Account` and `Transfer` entities of the <<graphOracleQuickStart, quick start>>, the generator runs:

[source,sql]
----
CREATE TABLE "ACCOUNTS" ("ID" NUMBER(19) NOT NULL,"NAME" VARCHAR(255) NOT NULL, PRIMARY KEY("ID"))
CREATE TABLE "TRANSFER" ("ID" NUMBER(19) NOT NULL,"AMOUNT" FLOAT(126) NOT NULL,"TOID" NUMBER(19) NOT NULL,"ACCOUNTID" NUMBER(19) NOT NULL, PRIMARY KEY("ID"))
CREATE INDEX "IDX_TRANSFER_ACCOUNTID_TOID" ON "TRANSFER" ("ACCOUNTID", "TOID")
CREATE OR REPLACE PROPERTY GRAPH bank_graph
  VERTEX TABLES ("ACCOUNTS" KEY ("ID") LABEL Account PROPERTIES ("ID", "NAME"))
  EDGE TABLES ("TRANSFER" KEY ("ID")
    SOURCE KEY ("ACCOUNTID") REFERENCES "ACCOUNTS" ("ID")
    DESTINATION KEY ("TOID") REFERENCES "ACCOUNTS" ("ID")
    LABEL TRANSFERS PROPERTIES ("ID", "AMOUNT"))
----

`CREATE_DROP` drops the property graphs before the tables, with `IF EXISTS`; a drop that fails, for example because another table has a foreign key to a vertex table, is logged as a warning. With `CREATE`, existing tables are kept and each property graph is replaced, so it follows changes to the entities. Graph repositories save nodes only, so rows of edge tables are written with SQL or a ann:data.jdbc.annotation.JdbcRepository[] over an entity of the edge table, which also supplies the identifier of a relationship entity. `VALIDATE` does not check the tables of graph entities.

NOTE: Schema generation is meant for development and testing. In production, create the tables and property graphs with a migration tool such as https://micronaut-projects.github.io/micronaut-flyway/latest/guide/index.html[Flyway] or https://micronaut-projects.github.io/micronaut-liquibase/latest/guide/index.html[Liquibase].

=== Generating the schema with R2DBC

The R2DBC schema generator creates the tables of the graph entities and the property graphs named by the ann:data.oracle.graph.r2dbc.annotation.OracleGraphR2dbcRepository[] repositories of the connection factory, with the same statements as the <<graphOracleSchema, JDBC schema generator>>:

[configuration]
----
r2dbc:
  datasources:
    default:
      schema-generate: CREATE_DROP
----

Rows of edge tables are written with SQL or a ann:data.r2dbc.annotation.R2dbcRepository[] over an entity of the edge table. R2DBC schema generation does not support `VALIDATE`.
