Graph entities are mapped with the annotations of the `io.micronaut.data.graph.annotation` package, which build on the Micronaut Data mapping model.

[cols="1,3"]
|===
|Annotation |Purpose

|ann:data.graph.annotation.Node[]
|Maps a class to a node. The label defaults to the simple name of the class. `labels` sets several labels.

|ann:data.graph.annotation.Relationship[]
|Maps a property to relationships. The type defaults to the property name in upper snake case, for example `actedIn` becomes `ACTED_IN`. `direction` is `OUTGOING` by default, or `INCOMING` or `UNDIRECTED`. A collection maps to many relationships, any other type to one.

|ann:data.graph.annotation.RelationshipProperties[]
|Maps a class whose instances are relationships with properties.

|ann:data.graph.annotation.TargetNode[]
|Marks the property of a relationship class that holds the node at the far end.

|ann:data.graph.annotation.RelationshipId[]
|Marks the identifier of a relationship class, generated by the database.

|ann:data.annotation.MappedProperty[]
|Renames a property.
|===

Nodes are identified by an ann:data.annotation.Id[] property. Identifiers can be:

* Assigned by the application, such as the title of a movie. Saving merges the node on its identifier, except for an entity with a ann:data.annotation.Version[] property, see <<graphIndexesAndLocking, optimistic locking>>.
* Generated by Micronaut Data, such as a `UUID` annotated with ann:data.annotation.AutoPopulated[].
* Generated by the database, with ann:data.annotation.GeneratedValue[]. A `String` holds the Neo4j element identifier and a `Long` the numeric identifier.

== Saving relationships

Saving an entity writes its node, then saves the nodes it relates to and merges the relationships between them. A related node that has an identifier is updated rather than created again, unless the relationship declares otherwise, see <<graphCascade, Cascading to related nodes>>. Saving does not remove relationships missing from a collection: use an explicit query to delete relationships.

Each `save`, `update`, `saveAll`, `updateAll` and `delete` joins the active transaction, or runs in a transaction of its own when none is active, so the statements of a cascading save either all apply or none: a save whose related node cannot be written leaves no node behind, and a versioned `updateAll` that finds a node changed since it was read writes nothing.

On Neo4j and Apache AGE, `saveAll` and `updateAll` write the nodes of one entity with a single `UNWIND` query per kind of write: nodes to create, nodes to update and nodes whose `@Version` is checked. The nodes a relationship property relates an entity to are written the same way, and its relationships are merged with one `UNWIND` query per set of relationship properties: saving a person who follows ten people runs one query for the people and one for the `FOLLOWS` relationships. A relationship entity with an identifier is written on its own instead, as two of them may connect the same nodes: it is updated by its identifier, or created when no relationship has it. Reactive repositories batch their writes the same way. Entity events still run for each entity, an instance passed more than once is written once, and the relationships of each node are written after all the nodes. A batch with two instances that have the same identifier is written one instance at a time, so that they conflict as two saves do. When a versioned `updateAll` finds a node that was changed since it was read, its query updates none of the nodes and fails with `OptimisticLockException`; likewise a `saveAll` of new versioned entities inserts none of them when one of their identifiers is taken. Apache AGE writes nodes with assigned identifiers one at a time, as it only merges the first node of an `UNWIND`.

=== Cascading to related nodes

By default a save cascades to the related nodes: a node without an identifier is created and one with an identifier is updated, so its properties are written again and its `@Version` advances. The `cascade` member of ann:data.graph.annotation.Relationship[] limits what a save does to the related nodes, with the values of `Relation.Cascade`:

* `ALL`, the default, creates new related nodes and updates existing ones.
* `PERSIST` creates new related nodes and links existing ones without updating them.
* `UPDATE` updates existing related nodes; a new one cannot be linked, and the save fails.
* `NONE` merges the relationship only: the related node must already exist with an identifier.

Relationships are not loaded unless a finder asks for them with ann:data.annotation.Join[], see <<graphTraversal, Querying Relationships>>. Collections of relationships that were not fetched are empty.

== Encoding values

Property and parameter values are encoded into values the database accepts by the encoder registered for their type in api:data.graph.runtime.GraphValueEncoders[], or for their nearest supertype. Strings, booleans, temporal values and the `long`, `int`, `short`, `byte`, `double` and `float` number types are written as they are, enums by name, and collections and maps element by element. `BigDecimal`, `BigInteger`, `UUID`, `URI`, `URL`, `Locale` and `Currency` values are written as strings, so a range finder on a `BigDecimal` or `BigInteger` property compares strings rather than numbers: use a `Long` or `Double` property where the order matters. A value of a type with no encoder fails with a `DataAccessException` naming the type. Each database replaces encoders for types it stores differently: Apache AGE writes temporal values as ISO-8601 strings, for example.

A bean of type api:data.graph.runtime.GraphValueEncoderRegistrar[] adds encoders for application types, or replaces those of the database:

== Reading with Micronaut Serialization

Nodes and relationships are read with https://micronaut-projects.github.io/micronaut-serialization/latest/guide/[Micronaut Serialization]. ann:data.graph.annotation.Node[] and ann:data.graph.annotation.RelationshipProperties[] make a class `@Serdeable`, so no further annotation is needed. Records, and classes with a public no-argument constructor and setters, get a deserializer generated at compile time. Other classes, such as a class that sets some properties through its constructor and others through setters, and Kotlin classes, are read by the deserializer Micronaut Serialization builds at runtime.

Saving does not use Micronaut Serialization: entities are written through their bean introspections.

The mapping of an entity to the database does not affect its JSON: a property renamed with `@MappedProperty` or by a naming strategy keeps its Java name in JSON, and a `@Transient` property is part of it. Other `@MappedEntity` classes in the application are not made `@Serdeable` by the graph annotation processor.
