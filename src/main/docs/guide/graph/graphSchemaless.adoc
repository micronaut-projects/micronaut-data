Nodes in a graph rarely share a fixed schema. A ann:data.graph.annotation.DynamicAttributes[] property holds every property of a node that its entity does not declare:

snippet::example.Pet[project-base="doc-examples/neo4j-example", source="main", tags="pet", languages="java,kotlin,groovy,python"]

<1> api:data.graph.model.DynamicAttributeHolder[] adds map-like access to the schemaless properties.
<2> The map receives the properties the class does not declare when a node is read, and its entries are written when the entity is saved.
<3> The holder reads and writes through this map.

Each language accesses the properties in its own style:

snippet::example.PetRepositorySpec[project-base="doc-examples/neo4j-example", tags="schemaless", indent="0", languages="java,kotlin,groovy,python"]

<1> Set a property that the class does not declare. Java calls `set`, Kotlin uses index syntax, Groovy property or subscript syntax, and Python the dictionary.
<2> Read it back.
<3> Query it with an explicit query.

[cols="1,2"]
|===
|Language |Syntax

|Java
|`pet.set("goesInPatch", true)` and `pet.get("goesInPatch")`

|Kotlin
|`pet["goesInPatch"] = true` and `pet["goesInPatch"]`

|Groovy
|`pet.goesInPatch = true`, `pet['goesInPatch']`

|Python
|`pet.attributes["goesInPatch"] = True`
|===

Values must be types the database stores: strings, numbers, booleans, temporal values and lists of those. Setting a value to `null` removes the property when the entity is saved. As schemaless properties are not known at build time, finders cannot refer to them. Use an explicit query instead.

Oracle property graphs store the map in a JSON column of the vertex table, named after the property, whose entries are read as properties of the node. Schema generation creates the column. Dynamic labels and dynamic relationships are not supported by Oracle.

== Dynamic labels

A collection of strings annotated with ann:data.graph.annotation.Labels[] holds the labels of a node beyond those its entity declares. Saving adds them to the node and reading collects them. Dynamic labels are supported by Neo4j.

== Dynamic relationships

A map annotated with ann:data.graph.annotation.DynamicRelationships[] holds the outgoing relationships of a node whose types its entity does not declare. Each key is a relationship type and each value lists the nodes at the far end:

snippet::example.Pet[project-base="doc-examples/neo4j-example", source="main", tags="relationships", languages="java,kotlin,groovy,python"]

<1> The map holds the relationships of undeclared types, keyed by type.

Saving an entity saves the nodes in the map and links them with `MERGE`, so saving it again does not duplicate its relationships. Reading an entity collects every outgoing relationship whose type is not declared by one of its ann:data.graph.annotation.Relationship[] properties, and maps each target node to the entity whose label it carries:

snippet::example.PetRepositorySpec[project-base="doc-examples/neo4j-example", tags="dynamicRelationships", indent="0", languages="java,kotlin,groovy,python"]

<1> Add a relationship of a type the entity does not declare.
<2> Saving the entity saves the target node and the relationship.
<3> Reading the entity reads its relationships back by type.

Only the owning node writes and reads the map. Removing an entry does not delete the relationship from the database. Use an explicit query to delete it. Dynamic relationships are supported by Neo4j. Apache AGE and Oracle property graphs reject them at build time.

The read has no limit. Every read of the entity, by any finder, collects all of its undeclared relationships and their target nodes, so a node with many of them is costly to read, and paging bounds the entities only. Keep the map for nodes with few undeclared relationships. Declare a relationship whose size grows with ann:data.graph.annotation.Relationship[], so that it is loaded only by the finders that join it.
