Micronaut Data MongoDB supports the full-text search API described in the <<sqlTextSearch, SQL section>> on top of MongoDB's `$text` operator and text indexes, or on top of MongoDB Search (`$search`) when the entity is annotated with ann:data.mongodb.annotation.MongoSearchIndex[]. The repository API is the same; this section lists what MongoDB adds and what it cannot do.

NOTE: Full-text search is experimental. The `$text` operator is available on every MongoDB deployment; `$search` needs MongoDB Atlas or the https://www.mongodb.com/docs/atlas/cli/current/atlas-cli-deploy-docker/[Atlas local deployment] (`mongodb/mongodb-atlas-local`).

== Mapping

Annotate the entity with ann:data.annotation.search.Searchable[] and the indexed properties with ann:data.annotation.search.SearchField[]:

snippet::example.Book[project-base="doc-examples/mongo-search-example", source="main", tags="entity"]

<1> `language` becomes the text index's `default_language` and the `$language` of every query.
<2> `weight` becomes the index weight of the field (`HIGH` is 10, `MEDIUM` 5, `LOW` 2, `LOWEST` 1).
<3> A property without a declared weight gets weight 1.

A property annotated with ann:data.annotation.search.Language[] becomes the index's `language_override`, so each document can carry its own language.

When `micronaut.data.mongodb.create-collections` is enabled, Micronaut Data creates the text index together with the collection, named `<collection>_text` unless `@Searchable(name)` says otherwise. A collection can have only one text index, so all search fields of an entity go into it. An existing text index is kept as it is, whatever its name: when the search fields, their weights or the languages of the entity change, Micronaut Data logs a warning instead of rebuilding the index, and the new mapping applies once the index is dropped and created again.

== Searching

snippet::example.BookRepository[project-base="doc-examples/mongo-search-example", source="main", tags="repository"]

<1> api:data.repository.SearchRepository[] adds `search` and `countHits`.
<2> `$text` always searches the whole text index, so a property keyword such as `findByTitleSearch` matches any search field of the entity, not only the title. A property keyword on a property that is not in the text index, one without `@SearchField` or one of a joined entity, is rejected at compile time.
<3> A `search` method returning `SearchResults` adds the `textScore` as the score and sorts by it in an aggregation.
<4> `SearchPhrase` quotes the whole string, which MongoDB matches as a phrase.
<5> Search keywords combine with other predicates in the same `$match`.

snippet::example.BookService[project-base="doc-examples/mongo-search-example", source="main", tags="search"]

The search string is translated to MongoDB's `$search` syntax at bind time: any term matches by default, quoted phrases are required, `-` excludes a term, and `OR` groups are flattened because MongoDB already matches any term. `SearchAll` quotes every term, which makes MongoDB require all of them; because MongoDB matches a quoted term literally, `SearchAll` loses stemming, so `searchByTitleSearchAll("programming languages")` does not find "The Rust Programming Language" although `search("languages")` does. `SearchAll` cannot be combined with `OR`, and a search string that does so fails with an `UnsupportedOperationException` that the application can turn into a client error. Because MongoDB requires every quoted phrase, a phrase in an any-term search is required too: `coffee "french press"` matches only documents containing the phrase.

The query sets `$language` to the entity's language, which is also the text index's `default_language`, so a document with its own language in the `language_override` field is still indexed with that language; only the search string is stemmed with the entity's.

A api:data.model.search.SearchQuery[] passed to `search(SearchQuery)` runs the same `$text` aggregation at runtime, as described in the <<sqlTextSearch, SQL full-text search section>>; as `$text` always searches the whole index, a query whose `fields` name only some of the search fields fails when the method runs with an api:data.model.search.UnsupportedSearchFeatureException[] for `FIELD_SCOPE` rather than silently searching every field. The `PREFIX` and `FUZZY` modes also fail when the method runs.

The `SearchNative` keyword and `SearchQuery.syntax(SearchSyntax.NATIVE)` bind the string as the `$search` string of `$text` unchanged, so MongoDB's own rules apply (`programming -kotlin`); as `$text` searches the whole text index, the native string reaches no field the other modes do not.

== MongoDB Search

Annotating a searchable entity with ann:data.mongodb.annotation.MongoSearchIndex[] switches the entity's search from `$text` to a `$search` aggregation stage over the search fields, which adds field scoping, prefix and fuzzy matching, highlighting and minimum score restrictions:

snippet::example.Article[project-base="doc-examples/mongo-search-example", source="main", tags="entity"]

<1> The language picks the Lucene analyzer of the index, `lucene.english` for `english`; `@MongoSearchIndex(analyzer)` overrides it.
<2> The name of the search index, `default` unless set.
<3> The index weights become query-time boosts of the field, `score: { boost: { value: 10 } }` for `HIGH`.
<4> A api:data.model.vector.Vector[] property with a `@Column(length)` dimension is indexed for `$vectorSearch`, see <<mongoVectorSearch, below>>.

When `micronaut.data.mongodb.create-collections` is enabled, Micronaut Data creates the search index together with the collection, mapping every search field as a `string` with the analyzer; `@MongoSearchIndex(dynamic = true)` also maps the remaining fields dynamically. The indexes are built asynchronously, so a document saved right before a search may not be found yet. On a deployment without MongoDB Search the indexes cannot be created and a warning is logged.

snippet::example.ArticleRepository[project-base="doc-examples/mongo-search-example", source="main", tags="repository"]

<1> A property keyword searches only that property with `$search`, unlike `$text`.
<2> `SearchPrefix` renders a `wildcard` operator over the analyzed field. The wildcard matches the indexed tokens, which a language analyzer such as `lucene.english` has stemmed, so a prefix longer than the stem, such as `runni` for `running` (indexed as `run`), finds nothing. For search-as-you-type, index the field with `lucene.standard` through `@MongoSearchIndex(analyzer)`, or keep prefixes short.
<3> `SearchFuzzy` renders a `text` operator with `fuzzy: { maxEdits: 1 }`.
<4> A trailing api:data.model.vector.search.Score[] parameter keeps the hits whose `searchScore` is at least its value.
<5> The other predicates follow the `$search` stage in a `$match`; a search predicate can neither be part of an `OR` nor be negated.
<6> A vector finder renders a `$vectorSearch` stage, see <<mongoVectorSearch, below>>.

The search string grammar is rendered into `compound` operators at bind time: every term becomes a `text` operator over the searched paths, a quoted phrase a `phrase` operator, a negated term a `mustNot` clause, and `OR` groups `should` clauses. `SearchAll` puts the terms in `must`, so every one is required.

With `SearchNative` or `SearchQuery.syntax(SearchSyntax.NATIVE)` the string is passed unparsed to one `queryString` operator per searched path, with that path as its `defaultPath` and the path's boost as its `score.boost`, and a document matching any of them matches. `queryString` accepts `field:value`, which reaches any path of the search index, including the fields `@MongoSearchIndex(dynamic = true)` maps, as well as wildcard, regular expression and range syntax, so pass only trusted input, as described in the <<sqlTextSearch, SQL full-text search section>>. Because each path is queried on its own, an exclusion such as `programming AND NOT kotlin` only excludes documents with both words in the same field.

`search(SearchQuery)` honours the `fields`, `mode`, `highlight` and `minScore` options. Highlights are read from the `searchHighlights` metadata and returned as one fragment per field with the hits wrapped in `<em>` tags, like the other stores. The relevance score is the `searchScore`.

NOTE: A `SearchResults` query, with `$text`, `$search` or `$vectorSearch`, adds the relevance score to each document as a field named `mn_score` and each highlight as a field named `mn_hl_<property>`, and removes them before the entity is decoded. These names are reserved: a stored field named `mn_score`, or one whose name starts with `mn_hl_`, is not mapped to the entity by a `SearchResults` query.

[[mongoVectorSearch]]
=== Vector and hybrid search

An entity with a `@MongoSearchIndex` also gets a vector search index, named by `@MongoSearchIndex(vectorIndex)` (`vector` unless set), with one `vector` field per api:data.model.vector.Vector[] property, whether or not the entity has search fields. The dimension comes from the property's `@Column(length)` and the similarity from `@MongoSearchIndex(similarity)`, `COSINE` unless set (`EUCLIDEAN` and `DOT_PRODUCT` are the others); a vector property without a dimension is not indexed and a warning is logged. A definition MongoDB rejects, such as a dimension above its limit, fails the startup. An existing vector index of that name is kept as it is: when the vector properties, their dimensions or the similarity change, Micronaut Data logs a warning instead of rebuilding the index, and the new mapping applies once the index is dropped and created again.

The vector search API of the <<sqlVectorType, SQL stores>> then runs on the index: a derived finder such as `searchByEmbeddingNear(Vector, Score)` or `findTop5ByEmbeddingNear(Vector, Double)` renders a `$vectorSearch` stage as the first stage of the aggregation, with the query vector, `limit` set from the method's limit or the page requested at runtime and `numCandidates` ten times that, followed by a `$match` on the maximum distance and the other predicates. The relevance score of a api:data.model.vector.search.SearchResults[] is the distance derived from the `vectorSearchScore` according to `@MongoSearchIndex(similarity)` (`2 - 2 * score` for `cosine` and `dotProduct`, `1 / score - 1` for `euclidean`), so results are comparable with the other stores.

Hybrid search with `SearchQuery.vector(...)` runs one `$rankFusion` aggregation whose input pipelines are the `$search` stage and the `$vectorSearch` stage, each cut to `candidates` hits, combined with reciprocal rank fusion under the query's weights; the fused score is read from `{ $meta: "score" }`. `$rankFusion` needs MongoDB 8.1 or later at feature compatibility version 8.1 or later: when the server rejects the stage as unknown (error code 40324) or not allowed (error code 224), that hybrid search falls back to fusing in memory, a warning is logged once, and the later hybrid searches of the application fuse in memory directly until it restarts. Any other error of the `$rankFusion` aggregation is thrown. Because the stage fixes the rank constant at 60 and carries no highlights, a query with another `rankConstant` or with highlighting runs the `$search` and the `$vectorSearch` aggregations separately and fuses their rankings in memory, as described in the <<sqlTextSearch, SQL full-text search section>>, with the same scores. A `$search` and a `$vectorSearch` stage cannot otherwise share one aggregation, so a derived hybrid finder such as `hybridSearchByTitleSearchAndEmbeddingNear(String, Vector)` runs through the same fusion as `SearchQuery.vector(...)` rather than as one criteria query, and a derived method combining a search keyword and a vector predicate without the `hybridSearch` prefix, such as `searchByTitleSearchAndEmbeddingNear`, is rejected at compile time. The other predicates of a vector query are applied after the stage as a `$match`, so they filter the `limit` nearest candidates rather than the whole collection. A vector query without a `Top` limit or a `Pageable` returns the 100 nearest neighbours, and a page must end within the first 10,000, the most `numCandidates` MongoDB accepts.

== Limitations

|===
|Feature |MongoDB `$text` |MongoDB Search (`$search`)

|Field scoping (`findByTitleSearch` matching only `title`) |not supported, every search field is searched |supported
|A property keyword on a property without `@SearchField` or of a joined entity |rejected at compile time, as the property is not in the text index |the property must be mapped by the search index
|Stemming in `SearchAll` |not supported, every term is matched literally |follows the analyzer of the search index
|Vector search and hybrid search |not supported |supported, `$vectorSearch` with the similarity of the vector index, and `$rankFusion` for hybrid search on MongoDB 8.1+
|`SearchPrefix` and `SearchFuzzy` |not supported, rejected at compile time |supported
|Highlighting |not supported; `@SearchField(highlightable = true)` is ignored by derived `SearchResults` methods, and `SearchQuery.highlight(...)` throws `UnsupportedSearchFeatureException` |supported
|Minimum score |not supported |supported
|Query-time boosts (`SearchQuery.boost`) |not supported |supported, as the operator's `score.boost`
|Edit distance (`SearchQuery.fuzzy(n)`) |not supported |supported, up to two edits
|Per-document language (`@Language`) |`language_override` |not supported, the analyzer is fixed per index
|Search with joins |the `$text` match is moved ahead of the join lookups, as MongoDB requires it in the first stage |`$search` must be the first stage, so joined queries are rejected at compile time
|Search predicate inside `OR` or `NOT` |rejected at compile time, as MongoDB only allows `$text` as a top-level condition |rejected, as the `$search` stage runs before the other conditions
|Cursored paging |not supported |not supported
|===

As on SQL stores, an unsorted `Pageable` or `Sort` parameter of a `SearchResults` method keeps the relevance order, best match first, with the document id breaking ties so consecutive pages neither repeat nor skip hits; a `Pageable` or `Sort` with orders replaces it.
