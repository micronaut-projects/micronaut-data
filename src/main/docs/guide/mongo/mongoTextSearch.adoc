Micronaut Data MongoDB supports the full-text search API described in the <<sqlTextSearch, SQL section>> on top of MongoDB's `$text` operator and text indexes, or on top of MongoDB Search (`$search`) when the entity is annotated with ann:data.mongodb.annotation.MongoSearchIndex[]. The repository API is the same; this section lists what MongoDB adds and what it cannot do.

NOTE: Full-text search is experimental. The `$text` operator is available on every MongoDB deployment; `$search` needs MongoDB Atlas or the https://www.mongodb.com/docs/atlas/cli/current/atlas-cli-deploy-docker/[Atlas local deployment] (`mongodb/mongodb-atlas-local`).

== Mapping

Annotate the entity with ann:data.annotation.search.Searchable[] and the indexed properties with ann:data.annotation.search.SearchField[]:

snippet::example.Book[project-base="doc-examples/mongo-search-example", source="main", tags="entity"]

<1> `language` becomes the text index's `default_language` and the `$language` of every query.
<2> `weight` becomes the index weight of the field (`HIGH` is 10, `MEDIUM` 5, `LOW` 2, `LOWEST` 1).
<3> A property without a declared weight gets weight 1.

A property annotated with ann:data.annotation.search.Language[] becomes the index's `language_override`, so each document can carry its own language.

When `micronaut.data.mongodb.create-collections` is enabled, Micronaut Data creates the text index together with the collection, named `<collection>_text` unless `@Searchable(name)` says otherwise. A collection can have only one text index, so all search fields of an entity go into it.

== Searching

snippet::example.BookRepository[project-base="doc-examples/mongo-search-example", source="main", tags="repository"]

<1> api:data.repository.SearchRepository[] adds `search` and `countHits`.
<2> `$text` always searches the whole text index, so a property keyword such as `findByTitleSearch` matches any search field of the entity, not only the title.
<3> A `search` method returning `SearchResults` adds the `textScore` as the score and sorts by it in an aggregation.
<4> `SearchPhrase` quotes the whole string, which MongoDB matches as a phrase.
<5> Search keywords combine with other predicates in the same `$match`.

snippet::example.BookService[project-base="doc-examples/mongo-search-example", source="main", tags="search"]

The search string is translated to MongoDB's `$search` syntax at bind time: any term matches by default, quoted phrases are required, `-` excludes a term, and `OR` groups are flattened because MongoDB already matches any term. `SearchAll` quotes every term, which makes MongoDB require all of them; it cannot be combined with `OR`.

A api:data.model.search.SearchQuery[] passed to `search(SearchQuery)` runs the same `$text` aggregation at runtime, as described in the <<sqlTextSearch, SQL full-text search section>>; its `fields` are ignored because `$text` always searches the whole index, and the `PREFIX` and `FUZZY` modes fail when the method runs.

== MongoDB Search

Annotating a searchable entity with ann:data.mongodb.annotation.MongoSearchIndex[] switches the entity's search from `$text` to a `$search` aggregation stage over the search fields, which adds field scoping, prefix and fuzzy matching, highlighting and minimum score restrictions:

snippet::example.Article[project-base="doc-examples/mongo-search-example", source="main", tags="entity"]

<1> The language picks the Lucene analyzer of the index, `lucene.english` for `english`; `@MongoSearchIndex(analyzer)` overrides it.
<2> The name of the search index, `default` unless set.
<3> The index weights become query-time boosts of the field, `score: { boost: { value: 10 } }` for `HIGH`.

When `micronaut.data.mongodb.create-collections` is enabled, Micronaut Data creates the search index together with the collection, mapping every search field as a `string` with the analyzer; `@MongoSearchIndex(dynamic = true)` also maps the remaining fields dynamically. The index is built asynchronously, so a document saved right before a search may not be found yet. On a deployment without MongoDB Search the index cannot be created and a warning is logged.

snippet::example.ArticleRepository[project-base="doc-examples/mongo-search-example", source="main", tags="repository"]

<1> A property keyword searches only that property with `$search`, unlike `$text`.
<2> `SearchPrefix` renders a `wildcard` operator over the analyzed field.
<3> `SearchFuzzy` renders a `text` operator with `fuzzy: { maxEdits: 1 }`.
<4> A trailing api:data.model.vector.search.Score[] parameter keeps the hits whose `searchScore` is at least its value.
<5> The other predicates follow the `$search` stage in a `$match`; a search predicate cannot be part of an `OR`.

The search string grammar is rendered into `compound` operators at bind time: every term becomes a `text` operator over the searched paths, a quoted phrase a `phrase` operator, a negated term a `mustNot` clause, and `OR` groups `should` clauses. `SearchAll` puts the terms in `must`, so every one is required.

`search(SearchQuery)` honours the `fields`, `mode`, `highlight` and `minScore` options. Highlights are read from the `searchHighlights` metadata and returned as one fragment per field with the hits wrapped in `<em>` tags, like the other stores. The relevance score is the `searchScore`.

== Limitations

|===
|Feature |MongoDB `$text` |MongoDB Search (`$search`)

|Field scoping (`findByTitleSearch` matching only `title`) |not supported, every search field is searched |supported
|`SearchPrefix` and `SearchFuzzy` |not supported, rejected at compile time |supported
|Highlighting and minimum score |not supported |supported
|Query-time boosts (`SearchQuery.boost`) |not supported |not supported, the index weights boost the fields
|Per-document language (`@Language`) |`language_override` |not supported, the analyzer is fixed per index
|Search with joins |`$text` must be the first stage, so joined queries fail at runtime |`$search` must be the first stage, so joined queries are rejected at compile time
|Search predicate inside `OR` |supported |rejected at compile time
|Cursored paging |not supported |not supported
|===

A `Pageable` or `Sort` parameter replaces the relevance order, as on SQL stores.
