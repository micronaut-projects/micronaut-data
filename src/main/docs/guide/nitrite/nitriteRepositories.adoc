[[nitriteRepositories]]
As seen in the <<nitriteQuickStart, Quick Start>> repositories are defined using the ann:data.nitrite.annotation.NitriteRepository[] stereotype annotation.

snippet::example.BookRepository[project-base="doc-examples/nitrite-example", source="main", tags="repository"]

Micronaut Data generates an implementation at compile time and executes queries via the Nitrite runtime implementation.

You can use standard repository method patterns:

- CRUD methods from `CrudRepository`
- Derived finders (for example `findByTitle`, `findByAgeGreaterThan`, `existsBySku`)
- Paging and sorting via `Pageable` and `Sort`
- Case-insensitive queries (for example `findByTitleIgnoreCase`)
- IN queries with collections and arrays (for example `findByTitleIn`)

== Save Method Upsert Semantics

The `save()` and `saveAll()` methods from `CrudRepository` use **upsert semantics**:

- If the entity's ID is `null`, a new document is inserted and the ID is generated
- If the entity has an existing ID, the document is updated (replaced) if found, or inserted if not found

This allows `save()` to be used for both creating new entities and updating existing ones. For explicit update operations, use the `update()` method or derived update methods (see <<nitriteQuickStart>>).

== DTO Projections

Micronaut Data Nitrite supports reflection-free https://micronaut-projects.github.io/micronaut-data/latest/guide/#dto[DTO projections] (see <<dto, shared DTO Projections guide>>) for repository methods that return a type other than the root entity. The DTO must be a concrete class (or record/data class) annotated with `@Introspected`, with a constructor or getter/setter pair for every projected property. Unlike JDBC/JPA, only concrete DTO types work: an `@Introspected` interface compiles but fails at runtime, because the Nitrite mapper instantiates the DTO via its `BeanIntrospection` constructor, and interfaces have none.

== Explicit JSON Queries

Nitrite does not support SQL-style `@Query` strings. User-authored `@Query` methods must use JSON filter documents with named placeholders.

Supported JSON filter operators include `$eq`, `$ne`, `$gt`, `$gte`, `$lt`, `$lte`, `$in`, `$nin`, `$null`, `$notNull`, `$between`, `$regex`, `$like`, `$not`, `$exists`, `$empty`, `$all`, and spatial operators (`$near`, `$within`, `$intersects`) when the spatial module is present. Full-text search uses Nitrite's `$text` filter on fields indexed with `@FullTextIndex`.

If a query needs to update fields, keep the filter document and update document separate and use named parameters. The runtime handles the Mongo-style `$set` wrapper used by some generated and JSON update queries before applying the Nitrite update.

For complex query logic, Micronaut Data provides:

- Criteria API repositories (see <<nitriteCriteriaSpecifications>>)
- `@Query` for explicit JSON filter queries

NOTE: Nitrite's runtime query execution supports the query strings encoded by Micronaut Data's document processor and the Nitrite query builder. If you use `@Query` with JSON, use named placeholders like `:name` and keep update documents separate from filter documents.
