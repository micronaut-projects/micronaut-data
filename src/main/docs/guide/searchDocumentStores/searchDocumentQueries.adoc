Derived finders, the criteria API and the search keywords all compile to one JSON request body per method, with the method parameters bound at runtime. The body is stored on the method's `@Query` annotation, so it can be inspected at compile time.

|===
|Repository predicate |Query DSL

|`findByAuthor(String)` |`term` on the field, or on `<field>.keyword` for an analysed search field
|`findByTitleIgnoreCase(String)` |`term` with `case_insensitive`
|`GreaterThan`, `LessThan`, `Between` |`range`
|`In` |`terms` (`ids` for the identity)
|`StartsWith`, `EndsWith`, `Contains`, `Like` |`wildcard` on the keyword field, pattern built at bind time
|`IsNull`, `IsNotNull`, `IsEmpty` |`exists`, negated inside `bool.must_not`
|`And`, `Or`, `Not` |`bool.must`, `bool.should` with `minimum_should_match: 1`, `bool.must_not`
|`Search`, `SearchAll`, `SearchPhrase`, `SearchPrefix`, `SearchFuzzy` |`simple_query_string` over the fields with their boosts
|`OrderBy...`, `Pageable`, `Sort` |`sort` on the keyword field, `from` and `size`
|===

== Full-text search

snippet::example.BookService[project-base="doc-examples/elasticsearch-search-example", source="main", tags="search"]

<1> `search(String)` searches every `@SearchField`, boosted by weight, and returns hits ordered by `_score`.
<2> Each hit holds the entity.
<3> The `_score` of the hit.
<4> `countHits` runs the same query through the count API.

The search string uses the portable grammar and is converted to Lucene `simple_query_string` syntax at bind time: `"quoted phrases"`, `-negated` terms, `OR` groups as `(a b) | (c)`, `SearchPrefix` as `term*` and `SearchFuzzy` as `term~1`. Special characters in terms are escaped, so user input is matched literally. `SearchAll` sets `default_operator` to `and`.

A api:data.model.search.SearchQuery[] passed to `search(SearchQuery)` builds the same `simple_query_string` request at runtime, as described in the <<sqlTextSearch, SQL full-text search section>>: its `fields` select the fields to search, with their declared weights as boosts, and its `mode` selects the operator and the prefix or fuzzy suffix, and its `highlight` properties are requested in the `highlight` clause and returned through `SearchResult.highlights()` with the default `<em>` tags.

== Paging and sorting

`Pageable` and `Sort` parameters set `from`, `size` and `sort`; a `Page` is built with `track_total_hits` so its total is exact. Sorting on an analysed search field sorts on its `keyword` sub-field.

A `CursoredPageable` pages with `search_after`: the request sorts by the pageable's sort with the entity id appended as a tiebreaker, and each hit's sort values become its cursor, so `CursoredPage.nextPageable()` and `previousPageable()` continue the scan without `from`, which the stores cap at 10,000 documents. A backward page reverses the sort and restores the order of the results.

== Optimistic locking and transactions

A `@Version` property maps to the document version. Micronaut Data writes with external versioning: a new entity is indexed at version `0`, an update increments the property and indexes with that version, and the store rejects the write with api:data.exceptions.OptimisticLockException[] when it already holds the document at that version or a later one. Reads take the version from the hit, so the property always reflects the stored document.

Elasticsearch and OpenSearch have no transactions. A repository method annotated with `@Transactional` fails at its first call with a configuration error naming the missing `TransactionOperations`; writes are visible according to the `refresh` policy and cannot be rolled back.

== Reactive and async repositories

Repositories may also extend api:data.repository.reactive.ReactorCrudRepository[] and api:data.repository.reactive.ReactorSearchRepository[], or the async, reactive-streams and Kotlin coroutine variants, and derived methods may return `Mono`, `Flux`, `Publisher` or `CompletableFuture`:

snippet::example.ReactiveBookRepository[project-base="doc-examples/elasticsearch-search-example", source="main", tags="reactive"]

<1> A reactive repository over the same entity and store; `ReactorSearchRepository` adds `search(String)`, `search(SearchQuery)` and `countHits` returning `Mono`.
<2> A `search` method returning `Mono<SearchResults<Book>>` projects the score and orders by it, like its blocking counterpart.
<3> Any derived finder can return a `Flux`.

Elasticsearch and OpenSearch run reactive and async repositories on their async clients through api:data.search.document.runtime.AsyncSearchTransport[], so no thread blocks on a request. A store that provides only a blocking api:data.search.document.runtime.SearchTransport[] still gets reactive repositories, run on the IO executor. `search(SearchQuery)` of api:data.repository.SearchRepository[] stays blocking.

== Limitations

- Joins, `@Where`, update queries (`updateBy...`) and subqueries are not supported; update entities with `update(...)`.
- `@Transactional` is not supported; see above.
- Highlighting, aggregations and the raw query DSL are not exposed yet.
