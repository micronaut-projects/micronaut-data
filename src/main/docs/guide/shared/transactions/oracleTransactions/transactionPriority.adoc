For Oracle JDBC and R2DBC transactions, Micronaut Data supports Oracle transaction priority with ann:transaction.annotation.OracleTransactional[].
Set the `priority` attribute to request the desired Oracle transaction priority:

[source.multi-language-sample,java]
----
import io.micronaut.transaction.annotation.OracleTransactional;

@OracleTransactional(priority = OracleTransactional.Priority.MEDIUM)
void updateInventory() {
    // ...
}
----
[source.multi-language-sample,kotlin]
----
import io.micronaut.transaction.annotation.OracleTransactional

@OracleTransactional(priority = OracleTransactional.Priority.MEDIUM)
open fun updateInventory() {
    // ...
}
----
[source.multi-language-sample,groovy]
----
import io.micronaut.transaction.annotation.OracleTransactional

@OracleTransactional(priority = OracleTransactional.Priority.MEDIUM)
void updateInventory() {
    // ...
}
----

When the transaction uses an Oracle connection, Micronaut Data sets the session `txn_priority` when the transaction begins and restores the priority the session had before when the transaction completes, also when the transaction runs on a connection opened by an outer scope, such as a method annotated with ann:data.connection.annotation.Connectable[]. Setting the priority and reading the previous one take one round trip to the database, restoring it another.
Non-Oracle databases ignore this property.

Setting the priority of the session (`ALTER SESSION SET "txn_priority"`) needs no privilege beyond `CREATE SESSION`. Reading the previous priority needs the privilege to read `V$PARAMETER`. The narrowest grant, which must be given by `SYS`, is:

[source,sql]
----
GRANT READ ON SYS.V_$PARAMETER TO app_user;
----

The `DB_DEVELOPER_ROLE` and `SELECT_CATALOG_ROLE` roles also allow it. Without the privilege the transaction still runs with the requested priority, and the session is reset to `HIGH`, the default priority of Oracle Database, when the transaction completes.

NOTE: Oracle transaction priority requires database support and appropriate Oracle priority transaction configuration.
Older Oracle versions that reject `txn_priority` continue without applying priority.
For the database-side wait targets and rollback mode, see the https://docs.oracle.com/en/database/oracle/oracle-database/26/admin/managing-transactions.html[Oracle transaction management documentation] and the https://docs.oracle.com/en/database/oracle/oracle-database/26/refrn/PRIORITY_TXNS_MODE.html[`PRIORITY_TXNS_MODE` reference].

If Oracle automatically rolls back a lower-priority transaction that is blocking a higher-priority transaction, it reports ORA-63300 while the blocking statement is executing. Subsequent statements can report ORA-63302 until the session acknowledges the rollback.

Micronaut Data JDBC and R2DBC transaction operations acknowledge the rollback and expose the failure as api:transaction.exceptions.OracleTransactionPriorityException[], so application code does not need to inspect Oracle error codes. Hibernate/JPA and Hibernate Reactive transaction managers continue to expose the underlying provider exception. Retry only after re-reading the current state, and make the operation idempotent when a retry is appropriate.

The transaction manager still performs the normal rollback and cleanup. The specific exception only makes the reason visible at the transaction boundary.

For example, an application can handle this contention separately from other transaction failures:

[source.multi-language-sample,java]
----
import io.micronaut.transaction.exceptions.OracleTransactionPriorityException;

try {
    checkoutService.checkout(accountId);
} catch (OracleTransactionPriorityException e) {
    // The transaction is already rolled back. Re-read the account before retrying.
}
----
[source.multi-language-sample,kotlin]
----
import io.micronaut.transaction.exceptions.OracleTransactionPriorityException

try {
    checkoutService.checkout(accountId)
} catch (e: OracleTransactionPriorityException) {
    // The transaction is already rolled back. Re-read the account before retrying.
}
----
[source.multi-language-sample,groovy]
----
import io.micronaut.transaction.exceptions.OracleTransactionPriorityException

try {
    checkoutService.checkout(accountId)
} catch (OracleTransactionPriorityException e) {
    // The transaction is already rolled back. Re-read the account before retrying.
}
----

The exception is a `TransactionException`, so existing transaction-exception handlers continue to apply. Only code that catches `DataAccessException` specifically needs to add a handler for this transaction-boundary failure.
